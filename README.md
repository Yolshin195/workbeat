# workbeat — телеграм-бот учёта рабочего времени (Rust + SQLite)

## Идея

Бот дисциплинирует рабочий день по методике 50/10: пользователь работает часовыми
интервалами, бот каждые 10 минут проверяет вовлечённость, привязывает время к
задачам и в конце дня формирует отчёт.

## 1. Структура рабочего дня

```
Рабочий день (8 часовых интервалов, до 8 "чистых" часов)
 └─ Часовой интервал (60 мин)
     ├─ 5 × десятиминутка работы (проверка "работаешь?")
     └─ 1 × десятиминутка отдыха (только если все 5/5 успешны)
```

- День стартует командой `/start_day`.
- Следующий часовой интервал **никогда не стартует автоматически** — пользователь
  сам запускает его командой/кнопкой, когда готов.
- После каждого завершённого часового интервала пользователь выбирает:
  **начать следующий интервал** или **пойти на обед**.
- Также после 4-го интервала бот сам предлагает пойти на обед (можно отказаться).
- Обед: кнопки "пошёл на обед" / "вернулся" — фиксируют start/end. Обеденное время
  **не входит** в 8-часовой рабочий день, хранится отдельным полем.
- День завершается командой `/finish_day`. Если она вызвана во время активного
  (незакрытого) часового интервала — интервал принудительно закрывается по
  фактически прошедшим десятиминуткам: ещё не начавшиеся десятиминутки не
  создаются, обязательный вопрос "что делали за этот час" в этом случае не
  блокирует завершение (ответ необязателен/может быть пустым).
- Если день начат (`/start_day`), но активного часового интервала нет (ещё не
  выбрали первую задачу и не нажали "начать интервал", пауза между интервалами,
  после обеда и т.п.) — бот периодически (раз в N часов простоя) спрашивает
  "Готовы продолжить работу?", пока пользователь не начнёт следующий интервал
  или не завершит день (`/finish_day`). Автоматического завершения дня по
  таймауту нет — день остаётся открытым, пока пользователь сам не вызовет
  `/finish_day`.
- Интенсивный опрос "молчания" (см. раздел 2, ежеминутные напоминания) действует
  **только внутри активного часового интервала** — вне интервала используется
  более редкий периодический опрос выше.

## 2. Логика десятиминутки (внутри часового интервала)

1. Бот запускает 10-минутный таймер.
2. По истечении — спрашивает: **"Ты работаешь?"**
   - **Да** → десятиминутка помечается как успешная, бот пишет "Отлично, продолжай",
     стартует следующая десятиминутка.
   - **Нет** → бот спрашивает "Что случилось?", ответ фиксируется как причина.
     Десятиминутка помечается как проваленная.
   - **Нет ответа** → бот раз в минуту в течение всей следующей десятиминутки
     спрашивает "Что случилось, почему не отвечаешь?". Если ответа так и нет —
     эта десятиминутка тоже фиксируется как проваленная. Итого: молчание превращает
     в проваленные сразу 2 десятиминутки (та, где не ответили на "работаешь?", и
     следующая — период ожидания ответа). Если пользователь всё же отвечает в
     любой момент восстановительной десятиминутки — ежеминутные напоминания
     прекращаются, а ответ сохраняется как `reason` **у обеих** десятиминуток
     (исходной, где не последовал ответ на "работаешь?", и восстановительной) —
     это один и тот же объясняющий текст на оба проваленных слота. Статус
     **обеих** десятиминуток остаётся проваленным: ответ внутри восстановительного
     окна останавливает эскалацию, но не отменяет уже случившийся провал.
3. После 5-й десятиминутки часовой интервал завершён (независимо от того,
   сколько из 5 было успешно — 5/5, 3/5 и т.д.).
   - Если **5/5 успешно** → добавляется 10-минутный отдых, он тоже засчитывается
     как рабочее время в задачу.
   - Если **не 5/5** → отдыха в счёт задачи нет, просто фиксируется провал.
4. Бот сообщает итог интервала ("Интервал завершён: 3/5" и т.п.) и спрашивает,
   что делали за этот час (обязательный вопрос, свободный текст в лог).
5. Пользователь может в любой момент написать "задача готова" — тогда оставшиеся
   десятиминутки этого часа автоматически идут в счёт следующей выбранной задачи.
   Уже начавшаяся в момент переключения десятиминутка (таймер идёт, либо бот уже
   спросил "работаешь?" и ждёт ответа, либо идёт восстановительный опрос) не
   прерывается и завершается под прежней задачей — "оставшиеся" означает только
   те десятиминутки, которые ещё не начались.

## 3. Задачи

- Задачи — отдельная сущность, создаются/редактируются через бота в любой момент
  (не обязательно заранее привязаны ко дню) — общий пул "готовые / не готовые".
- К интервалу привязывается одна задача из пула.
- Если задача не завершена к концу часа — автоматически продолжается в следующем
  интервале (после того как пользователь его запустит).
- Если задача завершена раньше конца часа — пользователь обязан выбрать
  следующую задачу для оставшихся десятиминуток.
- **Время задачи = сумма только успешных десятиминуток** (10 мин каждая),
  просуммированных по всем интервалам, где эта задача была активна.
  Отдых добавляется к задаче только за те интервалы, где было 5/5.
- У задачи есть необязательные приоритет (например, high / medium / low) и
  дедлайн (дата). Используются для сортировки/фильтрации пула задач при выборе
  следующей задачи.
- Статус `status` переключается по-разному в зависимости от источника:
  `ready`/`not_ready` — вручную пользователем при создании/редактировании
  задачи; в `in_progress` задача переходит автоматически, когда становится
  активной задачей часового интервала; в `done` — по команде "задача готова"
  (или явному действию "завершить задачу"), независимо от того, идёт ли сейчас
  часовой интервал.

## 4. Хранение времени и принцип таймеров

- Всё хранится в **UTC**.
- У пользователя есть поле `timezone` — используется только для отображения в
  отчётах (конвертация на лету).
- Базовая единица — `start_ts` / `end_ts` на каждом уровне (день, интервал,
  десятиминутка, обед), итоги считаются агрегацией.
- **Любой "таймер" в системе — это просто пара UTC-полей `start`/`stop`, а не
  запланированное фоновое задание.** Начать таймер = записать текущее время в
  поле `start`. Завершить = записать текущее время в `stop`. Узнать, сколько
  времени прошло: если `stop` ещё не заполнен — `now() - start`; если заполнен —
  `stop - start`. Никакого персистентного планировщика/расписания и
  идентификаторов запланированных задач в системе нет.
- Проактивные действия бота (вопрос "работаешь?" после 10 минут, ежеминутные
  напоминания при молчании, периодическое "готовы продолжить?" при простое)
  реализуются одним общим механизмом: процесс периодически (например, раз в
  30–60 секунд) опрашивает БД на предмет "у кого из открытых таймеров уже
  истекло нужное время", и по необходимости шлёт сообщение — а не заводит
  отдельный запланированный job на каждую десятиминутку/паузу. Это делает
  рестарт процесса не проблемой: после перезапуска ближайший опрос просто
  пересчитает `now() - start` заново по данным из БД, ничего не нужно
  восстанавливать вручную.

## 5. Отчёт

- `/report` — сводка в любой момент (текст в чат).
- `/finish_day` — закрывает день, тоже формирует финальную сводку.
- По запросу — экспорт в файл (CSV/текст).
- Содержание отчёта: суммарное отработанное время, по задачам (сколько минут на
  каждую), провальные десятиминутки и причины (для анализа продуктивности),
  время обеда, факт выполнения нормы 8 часов, а также ответы на обязательный
  вопрос "что делали за этот час" по каждому завершённому часовому интервалу.
- Отчёты доступны не только за день, но и за неделю/месяц (например,
  `/report_week`, `/report_month` или параметр периода в `/report`).
- Границы периода в `/report_week`/`/report_month` считаются по календарной
  дате в таймзоне пользователя (`users.timezone`): рабочий день "принадлежит"
  тому периоду, в который попадает его `started_at`, сконвертированный из UTC
  в таймзону пользователя — не UTC-дата.
- `/report`, вызванный посреди незавершённого часового интервала, включает уже
  завершённые десятиминутки текущего интервала (успешные/проваленные), но сам
  этот интервал не считается "закрытым" при подсчёте нормы 8 часов.
- Если `/report_week`/`/report_month` вызваны без явной даты — "сегодня" для
  определения текущей недели/месяца вычисляется из текущего момента (UTC),
  сконвертированного в `users.timezone`, а не как голая UTC-дата и не как
  локальная дата сервера — иначе для пользователей восточнее UTC ближе к концу
  дня расчёт периода может "съехать" на соседнюю неделю/месяц.

## 6. Схема БД (SQLite)

```sql
users (
    telegram_id     INTEGER PRIMARY KEY,
    timezone        TEXT DEFAULT 'UTC',
    created_at      DATETIME
);

tasks (
    id              INTEGER PRIMARY KEY,
    user_id         INTEGER REFERENCES users(telegram_id),
    title           TEXT,
    status          TEXT,      -- ready / not_ready / in_progress / done
    priority        TEXT,      -- high / medium / low, NULL если не задан
    deadline        DATE,      -- NULL если не задан
    created_at      DATETIME
);

work_days (
    id              INTEGER PRIMARY KEY,
    user_id         INTEGER REFERENCES users(telegram_id),
    started_at      DATETIME,
    finished_at     DATETIME,
    lunch_started_at DATETIME,
    lunch_ended_at   DATETIME,
    last_idle_prompt_at DATETIME -- когда последний раз спрашивали "готовы продолжить?"; NULL, если ещё не спрашивали в текущем простое
);

hour_intervals (
    id              INTEGER PRIMARY KEY,
    work_day_id     INTEGER REFERENCES work_days(id),
    started_at      DATETIME,
    ended_at        DATETIME,
    successful_count INTEGER,  -- 0..5, сколько десятиминуток из 5 успешны
    summary         TEXT       -- ответ на обязательный вопрос "что делали за этот час"
);

ten_min_checks (
    id              INTEGER PRIMARY KEY,
    hour_interval_id INTEGER REFERENCES hour_intervals(id),
    task_id         INTEGER REFERENCES tasks(id), -- задача, активная в момент этой десятиминутки
    is_recovery     BOOLEAN DEFAULT FALSE, -- восстановительная (ежеминутный опрос) или обычная десятиминутка
    started_at      DATETIME,
    ended_at        DATETIME,  -- NULL, пока десятиминутка ещё не завершена ("таймер идёт")
    status          TEXT,      -- worked / failed / no_response, NULL пока не завершена
    reason          TEXT       -- заполняется если failed / no_response
);
```

**Примечание:** `hour_intervals` намеренно не хранит `task_id` — один часовой
интервал может включать десятиминутки разных задач (правило "задача готова",
см. раздел 3), поэтому привязка к задаче живёт на уровне `ten_min_checks`.
10-минутный отдых, начисляемый при 5/5, засчитывается той задаче, которая была
привязана к последней (5-й) десятиминутке интервала.

`is_recovery` — единственное, что отличает две "роли" десятиминутки при
молчании (см. раздел 2, п.2): обычная (`is_recovery = false`) молчит 10 минут,
затем **один раз** спрашивает "работаешь?"; восстановительная
(`is_recovery = true`, создаётся автоматически вслед за проваленной обычной)
спрашивает "почему не отвечаешь?" **на каждом опросе** все свои 10 минут. Это
статический признак, выставляемый один раз при создании строки — не
состояние планировщика.

`work_days.last_idle_prompt_at` — тот же принцип "start/stop", применённый к
повторяющемуся напоминанию: это точка отсчёта для очередного сравнения
`now() - last_idle_prompt_at >= N часов`. При отправке напоминания поле
просто перезаписывается текущим временем — не нужен отдельный планировщик,
чтобы не спрашивать "готовы продолжить?" чаще, чем раз в N часов.

## 7. Открытые вопросы / на будущее (не блокируют MVP)

- Значение N (через сколько часов простоя бот присылает "Готовы продолжить
  работу?") решено сделать конфигурируемым параметром (переменная окружения/
  конфиг деплоя, см. план реализации) — конкретное значение по умолчанию не
  фиксируется спецификацией и подбирается на практике, это больше не
  блокирующая неопределённость для реализации.
