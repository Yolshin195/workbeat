# workbeat — телеграм-бот учёта рабочего времени (Rust + SQLite)

## Идея

Бот дисциплинирует рабочий день по методике 50/10: пользователь работает часовыми
интервалами, бот каждые 10 минут проверяет вовлечённость, привязывает время к
задачам и в конце дня формирует отчёт.

## 1. Структура рабочего дня

```
Рабочий день (8 часовых интервалов, до 8 "чистых" часов)
 └─ Часовой интервал (60 мин)
     ├─ 5 × десятиминутка работы (проверка "работаешь?")
     └─ 1 × десятиминутка отдыха (только если все 5/5 успешны)
```

- День стартует командой `/start_day`.
- Следующий часовой интервал **никогда не стартует автоматически** — пользователь
  сам запускает его командой/кнопкой, когда готов.
- После каждого завершённого часового интервала пользователь выбирает:
  **начать следующий интервал** или **пойти на обед**.
- Также после 4-го интервала бот сам предлагает пойти на обед (можно отказаться).
- Обед: кнопки "пошёл на обед" / "вернулся" — фиксируют start/end. Обеденное время
  **не входит** в 8-часовой рабочий день, хранится отдельным полем.
- День завершается командой `/finish_day`. Если она вызвана во время активного
  (незакрытого) часового интервала — интервал принудительно закрывается по
  фактически прошедшим десятиминуткам: ещё не начавшиеся десятиминутки не
  создаются, обязательный вопрос "что делали за этот час" в этом случае не
  блокирует завершение (ответ необязателен/может быть пустым).
- Если день начат (`/start_day`), но активного часового интервала нет (ещё не
  выбрали первую задачу и не нажали "начать интервал", пауза между интервалами,
  после обеда и т.п.) — бот периодически (раз в N часов простоя) спрашивает
  "Готовы продолжить работу?", пока пользователь не начнёт следующий интервал
  или не завершит день (`/finish_day`). Автоматического завершения дня по
  таймауту нет — день остаётся открытым, пока пользователь сам не вызовет
  `/finish_day`.
- Интенсивный опрос "молчания" (см. раздел 2, напоминания по расписанию) действует
  **только внутри активного часового интервала** — вне интервала используется
  более редкий периодический опрос выше.

## 2. Логика десятиминутки (внутри часового интервала)

**Принцип: один пропуск = один проваленный слот, без каскада.** Молчание не
плодит вторую "восстановительную" десятиминутку и не сбрасывает уже набранные
в этом часе успехи — проваленный слот закрывается сразу (коротким, номинальным
по длительности), а реальное время простоя видно не по длительности этого
слота, а по тому, насколько фактически растянулся весь час (см. раздел 5).

1. Бот запускает 10-минутный таймер очередной **рабочей** десятиминутки (1-й из
   5 в часе, либо следующей по счёту).
2. По истечении 10 минут бот спрашивает: **"Ты работаешь?"**
   - **Да** → десятиминутка закрывается как `Worked` (`ended_at` ≈ `started_at` +
     10 минут), бот пишет "Отлично, продолжай", сразу стартует следующая
     десятиминутка.
   - **Нет** → бот спрашивает "Что случилось, почему перестал работать?", ответ
     фиксируется в `reason`. Десятиминутка закрывается как `Failed`
     (`ended_at` ≈ `started_at` + 10 минут). Бот спрашивает "Готов продолжить?" —
     как только пользователь подтверждает, сразу стартует новая десятиминутка на
     этот же (следующий по счёту) слот; `started_at` новой десятиминутки — момент
     подтверждения, не момент закрытия предыдущей.
   - **Тишина (не ответил вообще)** → десятиминутка закрывается **сразу**, тем же
     номинальным `ended_at` ≈ `started_at` + 10 минут, статус `NoResponse`,
     `reason` пока пуст — она не ждёт возврата, чтобы закрыться. Дальше бот шлёт
     напоминания вернуться по расписанию из п.3 (каденс настраиваемый: по
     умолчанию первые 5 минут — раз в минуту, дальше — раз в 5 минут). Когда
     пользователь наконец откликается — тот же flow, что и для явного "нет": бот
     спрашивает "Что случилось?", ответ **дописывается как `reason` в уже
     закрытую** десятиминутку (сама она статус/`ended_at` не меняет — она так и
     остаётся коротким проваленным слотом), затем "Готов продолжить?" → "да" →
     стартует новая десятиминутка на этот же слот, `started_at` = момент
     подтверждения.
   - Час при этом **не сбрасывается** в любом из failed-сценариев — уже
     набранные в этом часе `Worked`-десятиминутки никуда не деваются, час просто
     растягивается по факту времени, пока не наберётся 5 закрытых рабочих
     десятиминуток.
3. **Расписание напоминаний** — настраиваемое (см. раздел 7), по умолчанию:
   первые `burst_window` минут — раз в `burst_interval` (по умолчанию 5 минут по
   1 напоминанию в минуту), затем — раз в `steady_interval` (по умолчанию раз в
   5 минут). Используется в двух местах с разным текстом и смыслом ожидания:
   - после провала рабочей десятиминутки из п.2 — напоминание "вернись к
     работе"/"что случилось" **до момента, пока пользователь не откликнется и не
     подтвердит готовность продолжить** (это и не закрывает, и не переоткрывает
     саму десятиминутку — она уже закрыта, ждём только начала следующей);
   - во время переработанного отдыха из п.4 — напоминание-проверка возврата,
     пока отдых не будет фактически закрыт.
4. Часовой интервал завершён, когда закрыто 5 рабочих десятиминуток (неважно,
   каким статусом — `Worked`/`Failed`/`NoResponse` — важно, что их 5 штук).
   - Если **все 5 — `Worked`** → бот пишет "Ты молодец, отдыхай 10 минут" и
     запускает десятиминутку отдыха; она тоже засчитывается как рабочее время
     в задачу.
     - Если пользователь откликается (например, кнопкой "Вернулся") в течение
       10 минут или сразу по их истечении — десятиминутка отдыха закрывается по
       факту, обычно ≈10 минут.
     - Если по истечении 10 минут отклика нет — это **не провал и не закрытие**:
       в отличие от рабочей десятиминутки, отдых **остаётся открытым**
       (`ended_at IS NULL`), а бот просто напоминает по расписанию из п.3, пока
       пользователь не вернётся. `ended_at` отдыха проставляется только по факту
       возврата, поэтому его итоговая длительность (например, 30 минут вместо
       10) фиксируется как есть и в отчёте идёт отдельной строкой "перерасход
       отдыха", без `reason` и без статуса "провален".
   - Если **не все 5 — `Worked`** → отдыха нет, интервал завершается сразу
     после закрытия 5-й десятиминутки.
5. Бот сообщает итог интервала ("Интервал завершён: 3/5" и т.п.) и спрашивает,
   что делали за этот час (обязательный вопрос, свободный текст в лог).
6. Пользователь может в любой момент написать "задача готова" — тогда оставшиеся
   десятиминутки этого часа автоматически идут в счёт следующей выбранной задачи.
   Уже начавшаяся в момент переключения десятиминутка (таймер идёт, бот ждёт
   ответа на "работаешь?", либо идёт ожидание подтверждения "готов продолжить?"
   после провала) не прерывается и завершается/стартует под прежней задачей —
   "оставшиеся" означает только те десятиминутки, которые ещё не начались.
7. Если день или интервал принудительно завершается (`/finish_day`, см.
   раздел 1) в момент, когда есть незакрытая десятиминутка (это может быть
   только переработанный отдых — рабочие десятиминутки, как описано в п.2,
   закрываются сразу и не остаются открытыми) — она принудительно закрывается:
   `ended_at = now`, фактическая длительность фиксируется как есть.

## 3. Задачи

- Задачи — отдельная сущность, создаются/редактируются через бота в любой момент
  (не обязательно заранее привязаны ко дню) — общий пул "готовые / не готовые".
- К интервалу привязывается одна задача из пула.
- Если задача не завершена к концу часа — автоматически продолжается в следующем
  интервале (после того как пользователь его запустит).
- Если задача завершена раньше конца часа — пользователь обязан выбрать
  следующую задачу для оставшихся десятиминуток.
- **Время задачи = сумма только успешных десятиминуток** (10 мин каждая),
  просуммированных по всем интервалам, где эта задача была активна.
  Отдых добавляется к задаче только за те интервалы, где было 5/5.
- У задачи есть необязательные приоритет (например, high / medium / low) и
  дедлайн (дата). Используются для сортировки/фильтрации пула задач при выборе
  следующей задачи.
- Статус `status` переключается по-разному в зависимости от источника:
  `ready`/`not_ready` — вручную пользователем при создании/редактировании
  задачи; в `in_progress` задача переходит автоматически, когда становится
  активной задачей часового интервала; в `done` — по команде "задача готова"
  (или явному действию "завершить задачу"), независимо от того, идёт ли сейчас
  часовой интервал.

## 4. Хранение времени и принцип таймеров

- Всё хранится в **UTC**.
- У пользователя есть поле `timezone` — используется только для отображения в
  отчётах (конвертация на лету).
- Базовая единица — `start_ts` / `end_ts` на каждом уровне (день, интервал,
  десятиминутка, обед), итоги считаются агрегацией.
- **Любой "таймер" в системе — это просто пара UTC-полей `start`/`stop`, а не
  запланированное фоновое задание.** Начать таймер = записать текущее время в
  поле `start`. Завершить = записать текущее время в `stop`. Узнать, сколько
  времени прошло: если `stop` ещё не заполнен — `now() - start`; если заполнен —
  `stop - start`. Никакого персистентного планировщика/расписания и
  идентификаторов запланированных задач в системе нет.
- Проактивные действия бота (вопрос "работаешь?" после 10 минут, напоминания
  при молчании по расписанию, периодическое "готовы продолжить?" при простое)
  реализуются одним общим механизмом: процесс периодически (например, раз в
  30–60 секунд) опрашивает БД на предмет "у кого из открытых таймеров уже
  истекло нужное время", и по необходимости шлёт сообщение — а не заводит
  отдельный запланированный job на каждую десятиминутку/паузу. Это делает
  рестарт процесса не проблемой: после перезапуска ближайший опрос просто
  пересчитает `now() - start` заново по данным из БД, ничего не нужно
  восстанавливать вручную.

## 5. Отчёт

- `/report` — сводка в любой момент (текст в чат).
- `/finish_day` — закрывает день, тоже формирует финальную сводку.
- По запросу — экспорт в файл (CSV/текст).
- Содержание отчёта: суммарное отработанное время, по задачам (сколько минут на
  каждую), провальные десятиминутки и причины (для анализа продуктивности),
  время обеда, факт выполнения нормы 8 часов, а также ответы на обязательный
  вопрос "что делали за этот час" по каждому завершённому часовому интервалу.
- Отдельно отчёт показывает **план vs факт по времени**: не только "3/5
  успешно", но и "фактически на этот час ушло 2 часа 30 минут вместо 1".
  Считается как `hour_intervals.ended_at - hour_intervals.started_at` (реальный
  разброс интервала — он растёт из-за пауз между провалом рабочей десятиминутки
  и стартом следующей, пока пользователь не отреагирует, а также из-за
  переработанного отдыха, см. раздел 2) минус номинальные 60 минут; по дню —
  сумма таких перерасходов по всем интервалам против номинальных 8×1ч. Это и
  есть числовой ответ на прокрастинацию: сколько часов реально просижено против
  скольких можно честно списать на задачи.
- Отчёты доступны не только за день, но и за неделю/месяц (например,
  `/report_week`, `/report_month` или параметр периода в `/report`).
- Границы периода в `/report_week`/`/report_month` считаются по календарной
  дате в таймзоне пользователя (`users.timezone`): рабочий день "принадлежит"
  тому периоду, в который попадает его `started_at`, сконвертированный из UTC
  в таймзону пользователя — не UTC-дата.
- `/report`, вызванный посреди незавершённого часового интервала, включает уже
  завершённые десятиминутки текущего интервала (успешные/проваленные), но сам
  этот интервал не считается "закрытым" при подсчёте нормы 8 часов.
- Если `/report_week`/`/report_month` вызваны без явной даты — "сегодня" для
  определения текущей недели/месяца вычисляется из текущего момента (UTC),
  сконвертированного в `users.timezone`, а не как голая UTC-дата и не как
  локальная дата сервера — иначе для пользователей восточнее UTC ближе к концу
  дня расчёт периода может "съехать" на соседнюю неделю/месяц.

## 6. Схема БД (SQLite)

```sql
users (
    telegram_id     INTEGER PRIMARY KEY,
    timezone        TEXT DEFAULT 'UTC',
    created_at      DATETIME
);

tasks (
    id              INTEGER PRIMARY KEY,
    user_id         INTEGER REFERENCES users(telegram_id),
    title           TEXT,
    status          TEXT,      -- ready / not_ready / in_progress / done
    priority        TEXT,      -- high / medium / low, NULL если не задан
    deadline        DATE,      -- NULL если не задан
    created_at      DATETIME
);

work_days (
    id              INTEGER PRIMARY KEY,
    user_id         INTEGER REFERENCES users(telegram_id),
    started_at      DATETIME,
    finished_at     DATETIME,
    lunch_started_at DATETIME,
    lunch_ended_at   DATETIME,
    last_idle_prompt_at DATETIME -- когда последний раз спрашивали "готовы продолжить?"; NULL, если ещё не спрашивали в текущем простое
);

hour_intervals (
    id              INTEGER PRIMARY KEY,
    work_day_id     INTEGER REFERENCES work_days(id),
    started_at      DATETIME,
    ended_at        DATETIME,
    successful_count INTEGER,  -- 0..5, сколько десятиминуток из 5 успешны
    summary         TEXT       -- ответ на обязательный вопрос "что делали за этот час"
);

ten_min_checks (
    id              INTEGER PRIMARY KEY,
    hour_interval_id INTEGER REFERENCES hour_intervals(id),
    task_id         INTEGER REFERENCES tasks(id), -- задача, активная в момент этой десятиминутки
    started_at      DATETIME,
    ended_at        DATETIME,  -- NULL, пока десятиминутка ещё не завершена ("таймер идёт")
    status          TEXT,      -- worked / failed / no_response, NULL пока не завершена
    reason          TEXT,      -- заполняется если failed / no_response
    last_reminder_at DATETIME  -- когда последний раз слали напоминание при молчании/переработке отдыха; NULL, если ещё не слали
);
```

**Примечание:** `hour_intervals` намеренно не хранит `task_id` — один часовой
интервал может включать десятиминутки разных задач (правило "задача готова",
см. раздел 3), поэтому привязка к задаче живёт на уровне `ten_min_checks`.
10-минутный отдых, начисляемый при 5/5, засчитывается той задаче, которая была
привязана к последней (5-й) десятиминутке интервала.

**Отдельной сущности/признака "восстановительная десятиминутка" в схеме нет.**
Молчание не создаёт вторую строку и не держит рабочий слот открытым — строка
`ten_min_checks` для проваленной по молчанию рабочей десятиминутки закрывается
сразу же (`ended_at` ≈ `started_at` + 10 минут, `status = no_response`,
`reason = NULL`), а `reason` может быть дописан в неё позже, когда пользователь
откликнется (см. раздел 2, п.2) — это единственный случай, когда `reason`
проставляется в уже закрытую строку. Различие "рабочий слот" vs "слот отдыха"
не хранится отдельным полем — это позиционный факт: 6-я по счёту десятиминутка
часа, создаваемая только когда предыдущие 5 закрыты со статусом `Worked`, и
есть отдых; именно поэтому только у неё `ended_at IS NULL` может держаться
дольше номинальных 10 минут — это единственный вид строки, которая по-настоящему
"ждёт" закрытия по факту возврата пользователя (см. раздел 2, п.4).

`last_reminder_at` — тот же принцип "start/stop", что и ниже у
`last_idle_prompt_at`: точка отсчёта для расписания напоминаний из раздела 2,
п.3, используется в двух разных ситуациях на одной и той же строке: (1) пока
десятиминутка отдыха ещё не закрыта (`ended_at IS NULL`) — как обычно, пока не
дождались возврата; (2) на уже закрытой проваленной рабочей десятиминутке,
последней в интервале (следующая ещё не началась) — как точка отсчёта для
напоминаний "вернись к работе"/"что случилось" в паузе перед стартом следующей
десятиминутки. В обоих случаях поле просто перезаписывается текущим временем
при каждом отправленном напоминании — не нужен отдельный планировщик, следующий
тик poll-цикла сравнивает `now() - last_reminder_at` с нужным по расписанию
интервалом.

`work_days.last_idle_prompt_at` — тот же принцип "start/stop", применённый к
повторяющемуся напоминанию: это точка отсчёта для очередного сравнения
`now() - last_idle_prompt_at >= N часов`. При отправке напоминания поле
просто перезаписывается текущим временем — не нужен отдельный планировщик,
чтобы не спрашивать "готовы продолжить?" чаще, чем раз в N часов.

## 7. Открытые вопросы / на будущее (не блокируют MVP)

- Значение N (через сколько часов простоя бот присылает "Готовы продолжить
  работу?") решено сделать конфигурируемым параметром (переменная окружения/
  конфиг деплоя, см. план реализации) — конкретное значение по умолчанию не
  фиксируется спецификацией и подбирается на практике, это больше не
  блокирующая неопределённость для реализации.
- Расписание напоминаний при молчании внутри десятиминутки (раздел 2, п.3) —
  тоже конфигурируемое, три параметра: `burst_window` (по умолчанию 5 минут),
  `burst_interval` (по умолчанию 1 минута — частота напоминаний внутри окна
  `burst_window`) и `steady_interval` (по умолчанию 5 минут — частота
  напоминаний после того, как `burst_window` истёк). Значения по умолчанию
  ориентировочные и могут быть скорректированы на практике, как и `N` выше.
