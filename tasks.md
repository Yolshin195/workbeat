# workbeat — план реализации (гексагональная архитектура)

Задачи идут строго по цепочке: каждая следующая опирается на результат предыдущей.
Внутри каждой задачи — что сделать, как тестировать, критерии приёмки. Делать
можно по одной, сохраняя контекст только текущей задачи и этого документа.

## Общая архитектура (ориентир для всех задач)

```
crates/
  domain/          — сущности, value objects, бизнес-правила (0 внешних зависимостей)
  application/      — use cases + порты (traits), зависит только от domain
  adapters/
    persistence-sqlite/  — реализация репозиториев (sqlx/rusqlite)
    scheduler-tokio/     — периодический poll-цикл (проверяет истёкшие таймеры в БД)
    telegram/             — teloxide-адаптер: входящие апдейты → use cases,
                            исходящие сообщения ← Notifier
  bin/app/          — composition root: собирает адаптеры + application, конфиг, запуск
```

Правило на все задачи: **domain** не знает про SQLite/Telegram/tokio-время.
**application** знает только про traits (порты), не про конкретные реализации.
Адаптеры реализуют порты и ничего не знают друг о друге.

## Задача 1. Каркас workspace и доменные сущности

**Цель:** создать Cargo workspace с крейтами `domain`, `application`,
`adapters/*` (пустые), `bin/app`. В `domain` — структуры и value objects из
SPEC.md раздела 6, без бизнес-логики переходов состояний, только сами типы.

**Что реализовать:**
- Value objects: `TelegramId`, `UtcTimestamp` (обёртка над `chrono::DateTime<Utc>`),
  `TimeZoneOffset`.
- Сущности: `User`, `Task` (+ `TaskStatus` enum: Ready/NotReady/InProgress/Done,
  + опциональный `TaskPriority` enum: High/Medium/Low, + опциональный
  `deadline: Option<NaiveDate>`), `WorkDay` (+ `last_idle_prompt_at: Option<UtcTimestamp>`
  — см. принцип таймеров в SPEC.md п.4), `HourInterval` (+ `summary: Option<String>`
  — ответ на обязательный вопрос "что делали за этот час"), `TenMinCheck`
  (+ `task_id: TaskId` — задача, активная в момент этой десятиминутки,
  + `last_reminder_at: Option<UtcTimestamp>` — точка отсчёта расписания
  напоминаний (переработанный отдых, ожидающий возврата, либо уже закрытая
  проваленная рабочая десятиминутка, ожидающая старта следующей), см. SPEC.md
  п.6, + `CheckStatus` enum: Worked/Failed/NoResponse). Признака
  "восстановительная десятиминутка" (`is_recovery`) в системе больше нет —
  см. правку раздела 2 SPEC.md от 2026-08-21: молчание закрывает рабочую
  десятиминутку сразу (без второй сущности), `reason` может быть дописан в уже
  закрытую строку.
- Все поля — как в схеме SQLite из SPEC.md, но как rust-типы (не строки для времени/enum).
  Важно: `task_id` живёт на `TenMinCheck`, а не на `HourInterval` — один часовой
  интервал может включать десятиминутки разных задач (правило "задача готова").
  Важно (принцип таймеров, SPEC.md п.4): у всех сущностей с длительностью
  (`WorkDay`, `HourInterval`, `TenMinCheck`) время хранится строго как пара
  `started_at`/`ended_at: Option<UtcTimestamp>` — никаких отдельных типов
  "таймер"/"job" в domain нет и не будет; "истекло ли время" — это всегда
  чистая функция от `now` и `started_at` (см. Задачу 2), а не что-то, что
  само себя планирует.
- Никаких `impl` с бизнес-логикой — только конструкторы и геттеры.

**Тестирование:**
- Unit-тесты на конструкторы: невалидные значения (например `successful_count > 5`)
  должны быть невозможны на уровне типов или возвращать `Result`.
- `cargo test -p domain` проходит без сети/файловой системы.

**Критерии приёмки:**
- `cargo build --workspace` собирается.
- `domain` не имеет зависимостей на tokio/sqlx/teloxide в `Cargo.toml`.
- Есть `README.md` в `domain/` с описанием сущностей.

**✅ Ремедиация выполнена (2026-08-21):** код `crates/domain` приведён к
актуальной схеме SPEC.md — `task_id` и `last_reminder_at` перенесены на
`TenMinCheck`, `HourInterval` лишился `task_id` и получил `summary`, `WorkDay`
получил `last_idle_prompt_at`. Конструкторы и unit-тесты обновлены,
`cargo build --workspace` и `cargo test -p domain` проходят.

## Задача 2. Доменные бизнес-правила (чистые функции, без портов)

**Зависит от:** Задача 1.

**Цель:** реализовать в `domain` чистую логику переходов состояний часового
интервала и десятиминуток — без ввода-вывода, только функции
`(текущее состояние, событие) -> новое состояние`.

**Что реализовать:**
- `WorkSlotPollDecision`: **чистая функция** `(elapsed_since_start: Duration,
  already_prompted: bool) -> WorkSlotPollOutcome`, где `WorkSlotPollOutcome` —
  одно из: `NoActionYet` / `AskAreYouWorking` (спросить "Ты работаешь?" один
  раз, когда `elapsed_since_start >= 10 мин` и ещё не спрашивали) /
  `ResolveNoResponse` (когда уже спрашивали, а ответа так и не было к
  следующему тику — закрыть **немедленно**: `ended_at = started_at + 10 мин`,
  `status = NoResponse`, `reason = None`). Управляет **только** открытой
  **рабочей** десятиминуткой (SPEC.md раздел 2, п.2) — никакого "окна
  ожидания" после закрытия здесь нет: молчание закрывает слот сразу, без
  второй сущности и без каскада на два проваленных слота.
- `ReminderScheduleDecision`: **чистая функция** `(elapsed_since_last_reminder:
  Duration, elapsed_since_wait_started: Duration, burst_window: Duration,
  burst_interval: Duration, steady_interval: Duration) -> bool` — "пора ли
  слать очередное напоминание". Общая для двух разных ситуаций из SPEC.md
  раздела 2, п.3: (а) десятиминутка отдыха, которая осталась открытой дольше
  10 минут, ждёт фактического возврата; (б) уже закрытая проваленная рабочая
  десятиминутка — последняя в интервале, следующая ещё не началась — ждёт,
  когда пользователь объяснит причину и подтвердит "готов продолжить". Логика:
  пока `elapsed_since_wait_started < burst_window` — сравнивать с
  `burst_interval`, иначе — со `steady_interval`. Пороговые константы
  (`burst_window`/`burst_interval`/`steady_interval`) не хардкодятся в
  domain — приходят параметром снаружи (конфигурируются, см. Задачу 13),
  сама функция лишь применяет их к переданным длительностям.
- `TenMinCheckState`: машина состояний для одной десятиминутки
  (Pending → Worked | Failed | NoResponse) по правилам из SPEC.md п.2. Никакого
  каскада на 2 десятиминутки нет: одно молчание — один проваленный слот.
  Единственная особенность: `reason` для `NoResponse`-слота, в отличие от
  `Failed`, может быть дописан **после** закрытия (когда пользователь наконец
  откликнется на уже закрытую десятиминутку) — это единственный легальный
  случай изменения уже закрытой строки, и явно тестируется отдельно.
- `IdlePromptDecision`: аналогичная чистая функция `(elapsed_since_last_prompt: Duration,
  idle_threshold: Duration) -> bool` для `PromptContinueIfIdle` — та же логика
  "elapsed ≥ порог", просто с другим порогом (`N` часов) и другой точкой отсчёта
  (`last_idle_prompt_at`, см. SPEC.md п.6). Концептуально похожа на
  `ReminderScheduleDecision`, но не унифицируется с ней специально: разный
  масштаб порога (часы против минут) и разная семантика (простой между
  интервалами, а не ожидание внутри активного интервала).
- `HourIntervalState`: агрегирует закрытые десятиминутки интервала → считает
  `successful_count` — количество **успешных** (`Worked`) среди них (провальные
  `Failed`/`NoResponse` в этот счёт не входят и не занимают место одной из 5
  нужных — они лишь добавляют интервалу ещё одну повторную десятиминутку, см.
  SPEC.md раздел 2, п.4) — и решает, закрыт ли рабочий этап: он закрыт ровно
  тогда, когда `successful_count == 5`, независимо от того, сколько при этом
  было провальных попыток и сколько десятиминуток в интервале всего. Отдых
  положен всегда, когда рабочий этап закрыт естественно (не принудительно
  через `/finish_day`, см. Задачу 8) — то есть фактически всегда, кроме
  принудительного завершения интервала с `successful_count < 5`. Также
  определяет **позиционный факт** "это слот отдыха" (десятиминутка,
  создаваемая сразу после того, как `successful_count` достиг 5) — этот флаг
  не хранится в БД, а вычисляется по количеству и статусам уже существующих
  десятиминуток интервала и передаётся вызывающим кодом в
  `WorkSlotPollDecision`/`ReminderScheduleDecision` там, где нужно различить
  поведение рабочего слота и слота отдыха.
- Функция расчёта времени задачи: сумма успешных десятиминуток + (отдых, если 5/5),
  по всем интервалам, привязанным к задаче.
- Функция определения дневной нормы: сколько из 8 часовых интервалов закрыто.
- Функция расчёта перерасхода (для отчёта, SPEC.md раздел 5): факт длительность
  интервала (`ended_at - started_at`) минус номинальные 60 минут; по дню — сумма
  таких перерасходов по всем интервалам минус номинальные 8×60 минут.

**Тестирование (обязательно табличные/parametrized тесты):**
- `WorkSlotPollDecision`: табличный тест — `elapsed = 9 мин` → `NoActionYet`;
  `elapsed = 10 мин, already_prompted = false` → `AskAreYouWorking`;
  `elapsed = 11 мин, already_prompted = true` → `ResolveNoResponse`.
- `ReminderScheduleDecision`: табличный тест на границах `burst_window` и на
  сравнении с `burst_interval`/`steady_interval` по обе стороны от неё.
- `IdlePromptDecision`: `elapsed_since_last_prompt < N часов` → `false`,
  `>= N часов` → `true`.
- Все комбинации 0..5 успешных десятиминуток (`successful_count`) → корректный
  расчёт времени задачи и признака "положен отдых"; отдельно — случай, когда
  среди закрытых десятиминуток интервала есть провальные вперемешку с
  успешными (например, `Worked, Failed, Worked, Worked, NoResponse, Worked,
  Worked` — итого 7 десятиминуток, но `successful_count = 5`) → рабочий этап
  закрыт, отдых положен, несмотря на то что закрытых десятиминуток больше 5.
- Сценарий "нет ответа" → проваливает ровно **один** слот (никакого каскада на
  2), интервал не сбрасывается, уже закрытые `Worked`-десятиминутки сохранены;
  отдельный тест на дозапись `reason` в уже закрытую `NoResponse`-десятиминутку
  при позднем отклике пользователя — статус и `ended_at` при этом не меняются.
- Сценарий переработанного отдыха: десятиминутка отдыха остаётся открытой
  дольше 10 минут, закрывается по факту возврата (например, 30 минут вместо
  10), это не провал (нет `reason`, статус не `Failed`/`NoResponse`).
- Сценарий смены задачи посередине часа (после 2-й из 5) → время корректно
  разбивается между двумя задачами (после ремедиации Задачи 1 это моделируется
  через `task_id` на каждом отдельном `TenMinCheck`, а не на `HourInterval`).
- Property-based тест (например `proptest`) на инвариант: сумма времени
  успешных (`Worked`) десятиминуток по задачам в рамках интервала никогда не
  превышает 60 минут (перерасход от провалов/отдыха в эту сумму не входит —
  он учитывается отдельно функцией расчёта перерасхода).

**Критерии приёмки:**
- 100% покрытие бизнес-правил юнит-тестами (без моков, чистые функции).
- Ни один тест не требует async/tokio.

## Задача 3. Порты (traits) в application

**Зависит от:** Задача 2.

**Цель:** описать в `application` все интерфейсы, через которые use cases будут
общаться с внешним миром — ещё без реализаций.

**Что реализовать (traits):**
- `UserRepository`, `TaskRepository`, `WorkDayRepository`, `HourIntervalRepository`,
  `TenMinCheckRepository` — CRUD/query методы, все `async_trait`, возвращают
  `Result<_, RepoError>`. Отдельно предусмотреть query-методы, нужные для
  периодического опроса (poll, см. Задачу 7/8/10) — единственного механизма
  проактивных сообщений в системе (SPEC.md п.4: никакого отдельного
  планировщика/job'ов нет, всё через "начался ли таймер и сколько прошло"):
  - `WorkDayRepository::find_open_without_active_interval()` — открытые
    `work_days` (`finished_at IS NULL`), у которых сейчас нет незакрытого
    `HourInterval` (кандидаты на `PromptContinueIfIdle`);
  - `TenMinCheckRepository::find_open()` — все `TenMinCheck` с `ended_at IS NULL`
    по всем активным интервалам (кандидаты на `WorkSlotPollDecision`, если это
    рабочий слот, либо на `ReminderScheduleDecision`, если это переработанный
    отдых — см. Задачу 2/7);
  - `TenMinCheckRepository::find_awaiting_resume()` — закрытые `TenMinCheck` со
    статусом `Failed`/`NoResponse`, которые являются последней по времени
    десятиминуткой своего ещё не закрытого `HourInterval` (то есть следующая
    десятиминутка ещё не началась) — кандидаты на `ReminderScheduleDecision` с
    текстом "вернись к работе"/"что случилось" (SPEC.md раздел 2, п.3); как
    только по этому слоту стартует новая десятиминутка, он перестаёт попадать
    в выборку на следующем тике.
  Все три нужны периодическому поллеру и одинаково исправно работают что на
  первом тике после старта процесса, что после рестарта — они просто читают
  текущее состояние из БД, никакого отдельного шага восстановления не требуется.
- `Clock` — `fn now(&self) -> UtcTimestamp` (для тестируемости времени). Это
  **единственный** порт, нужный use cases для работы со временем — никакого
  `Scheduler`/`JobId`/`schedule_once`/`cancel` в системе нет: вместо
  "запланировать job и не забыть отменить" вся проактивность реализована как
  периодический опрос (poll), считающий `now() - started_at` по данным из БД
  (см. SPEC.md п.4). Планировщика в application-порту действительно нет —
  цикл опроса (`tokio::time::interval`) целиком живёт в адаптере (Задача 10)
  и просто вызывает use cases каждый тик.
- `Notifier` (исходящий порт для интерфейсов) — `async fn send(&self, user: TelegramId, message: OutboundMessage)`.
  `OutboundMessage` — enum в domain или application, не привязан к Telegram
  (никаких `ChatId` из teloxide здесь). Обязательные варианты:
  `OutboundMessage::Text(String)` и
  `OutboundMessage::Document { filename: String, bytes: Vec<u8> }` (нужен для
  отправки CSV-экспорта из Задачи 9 как файла, а не текстом — без этого
  варианта Задача 12 не сможет реализовать отправку документа).

**Тестирование:**
- Для каждого порта — `mock`-реализация (через `mockall` или ручные фейки) в
  `application/src/testing.rs`, используемая последующими задачами.
- Компилируется без реализаций-адаптеров (только traits).

**Критерии приёмки:**
- `application` собирается, имея в зависимостях только `domain`, `async-trait`,
  `mockall` (dev-dependency), без sqlx/teloxide/tokio-runtime специфики (можно
  `tokio::time::Duration` как нейтральный тип, но не сам tokio runtime).

**✅ Выполнено (2026-08-21):** порты реализованы в `crates/application/src/ports`
(`UserRepository`, `TaskRepository`, `WorkDayRepository`, `HourIntervalRepository`,
`TenMinCheckRepository`, `Clock`, `Notifier` + `OutboundMessage`), ошибки —
типизированные (`RepoError`, `NotifierError`, `thiserror`). Ручные in-memory
фейки для всех портов — в `crates/application/src/testing.rs` (под
`#[cfg(test)]`), там же юнит-тесты на каждый фейк (`cargo test -p application`,
7 тестов). `application` зависит только от `domain`, `async-trait`, `thiserror`
(+ `mockall`/`chrono`/`pollster` как dev-dependencies); `cargo build --workspace`
и `cargo clippy -p application --all-targets` проходят чисто.

## Задача 4. SQLite-адаптер: миграции и репозитории

**Зависит от:** Задача 3.

**Цель:** реализовать все репозитории из Задачи 3 поверх SQLite (`sqlx` с
компилируемыми миграциями или `rusqlite`).

**Что реализовать:**
- SQL-миграции ровно по схеме из SPEC.md п.6 (актуальная ревизия: `task_id` и
  `last_reminder_at` — на `ten_min_checks`, а не `is_recovery` (этой сущности
  больше нет, см. ремедиацию Задачи 1); `hour_intervals.summary` для ответа на
  "что делали за этот час"; `work_days.last_idle_prompt_at`), включая колонки
  `priority`/`deadline` в `tasks` (оба NULL-able, без `NOT NULL`) и корректные
  объявленные типы для дат (`DATE` для `deadline`, `DATETIME` для остальных
  временных полей) (плюс индексы: по `user_id`, `work_day_id`,
  `hour_interval_id`, `ten_min_checks.task_id`, и частичные индексы на
  `ended_at IS NULL`/`finished_at IS NULL` там, где периодический опрос из
  Задачи 7/8/10 ищет "ещё не завершённые" строки — это самый частый запрос в
  системе, выполняется на каждом poll-тике; отдельный индекс/запрос под
  `find_awaiting_resume()` из Задачи 3 — по `hour_interval_id` среди
  закрытых строк со статусом `failed`/`no_response`, отсортированных по
  `ended_at` — нужен, чтобы дёшево найти последнюю закрытую десятиминутку
  ещё не завершённого интервала).
- Реализация каждого `*Repository` trait из Задачи 3 в `adapters/persistence-sqlite`.
- Маппинг rust enum ↔ TEXT в БД (явные `TryFrom`/`From`, никаких "magic strings"
  в бизнес-коде).

**Тестирование:**
- Интеграционные тесты на **временной SQLite БД** (`:memory:` или tempfile) для
  каждого репозитория: create → read → update round-trip.
- Тест на миграции: применяются с нуля без ошибок.
- Тест конкурентного доступа (2 параллельных tokio-задачи пишут в разные
  таблицы) — SQLite не должен падать (проверить `busy_timeout`/WAL режим).

**Критерии приёмки:**
- `cargo test -p adapters-persistence-sqlite` проходит на чистой БД в CI без
  внешних сервисов.
- Файл БД создаётся по пути из конфига, схема соответствует SPEC.md.

**✅ Выполнено (2026-08-21):** миграции — в
`crates/adapters/persistence-sqlite/migrations/0001_initial.sql`, ровно по
схеме README.md п.6 (`task_id`/`last_reminder_at` на `ten_min_checks`,
`hour_intervals.summary`, `work_days.last_idle_prompt_at`, nullable
`priority`/`deadline`, `DATE`/`DATETIME` типы), плюс индексы по
`user_id`/`work_day_id`/`hour_interval_id`/`task_id`, частичные индексы на

18 интеграционных тестов на временной SQLite БД (in-memory для

## Задача 6. Application: use cases управления задачами

**Зависит от:** Задача 5.

**Цель:** реализовать CRUD и переходы статусов сущности `Task` из SPEC.md
раздела 3. Без этой задачи Задача 7 (часовой интервал) не имеет способа
переключать `in_progress`/`done`, не обходя `TaskRepository` напрямую из
бизнес-логики, а Задача 11 (Telegram-адаптер) не сможет показывать/фильтровать
пул задач, не обращаясь к `TaskRepository` в обход `application` — что
нарушает архитектурное правило "use cases — единственная точка бизнес-логики".

**Что реализовать:**
- `CreateTask(user_id, title, priority: Option<TaskPriority>, deadline: Option<NaiveDate>) -> Task`
  — создаётся сразу в статусе `not_ready` или `ready` (на усмотрение параметра).
- `UpdateTask(task_id, title?, priority?, deadline?, status: Option<Ready|NotReady>)`
  — редактирование полей, задаваемых пользователем вручную; не позволяет
  выставить `in_progress`/`done` напрямую.
- `ListAvailableTasks(user_id, filter: Ready|NotReady|All) -> Vec<Task>` —
  список пула задач, отсортированный по приоритету (high → medium → low → без
  приоритета), затем по дедлайну (раньше — выше, без дедлайна — в конце).
- `MarkTaskInProgress(task_id)` / `MarkTaskDone(task_id)` — внутренние use
  cases, переиспользуемые Задачей 7 при старте интервала и по команде "задача
  готова"; не вызываются напрямую из Telegram-адаптера.

**Тестирование:**
- Unit-тесты на моках: сортировка пула по приоритету/дедлайну (табличный тест
  с несколькими комбинациями присутствия/отсутствия priority и deadline),
  фильтрация по статусу.
- Тест: `UpdateTask` не позволяет установить `in_progress`/`done` через
  пользовательское редактирование — только через `MarkTaskInProgress`/`MarkTaskDone`.

**Критерии приёмки:**
- Use cases не импортируют ничего из `adapters/*`.
- В Задаче 11 нет ни одного прямого вызова `TaskRepository` — только через use
  cases этой задачи.

**✅ Выполнено (2026-08-22, уточнено с автором задачи):** `CreateTask`,
`UpdateTask`, `ListAvailableTasks`, `MarkTaskInProgress`, `MarkTaskDone`
реализованы в `crates/application/src/use_cases`. По итогам уточнения у

сортировки и тест на частичное обновление/очистку полей) — на фейках из

## Задача 7. Application: use cases часового интервала и десятиминуток

**Зависит от:** Задача 6.

**Цель:** реализовать полный цикл часового интервала, используя бизнес-правила
из Задачи 2 и порты из Задачи 3.

**Что реализовать:**
- `StartHourInterval(work_day_id, task_id)` — старт только по явному действию
  пользователя, ошибка, если предыдущий интервал не закрыт; переводит задачу в
  `in_progress` через `MarkTaskInProgress` из Задачи 6; создаёт первую
  `TenMinCheck` (`task_id`, `started_at = now`).
- `SubmitTenMinAnswer(interval_id, answer: Yes|No, reason: Option<String>)` —
  закрывает **открытую** десятиминутку интервала (`ended_at = now`,
  `status = Worked` при `Yes`, `status = Failed` + `reason` при `No`, `reason`
  обязателен для `No`). Важно: счёт "сколько из 5 нужных" ведётся **только по
  успешным (`Worked`)** десятиминуткам — провальная десятиминутка не занимает
  место одной из 5 нужных, а лишь удлиняет интервал ещё на одну попытку
  (SPEC.md раздел 2, п.4). Дальше, без ожидания дополнительного подтверждения
  там, где по SPEC.md п.2 "Да" продолжает сразу:
  - если ответ `Yes` и это была **не 5-я успешная** десятиминутка интервала —
    сразу создаёт следующую `TenMinCheck` (`task_id` — текущая активная задача
    интервала, `started_at = now`);
  - если ответ `Yes` и это была **5-я успешная** десятиминутка интервала —
    сразу создаёт десятиминутку **отдыха** (тот же `task_id`, `started_at =
    now`) и шлёт "Ты молодец, отдыхай 10 минут"; рабочий этап интервала на
    этом закончен;
  - если ответ `No` — новая десятиминутка **не создаётся сразу**: интервал
    переходит в состояние "жду возврата" (последняя закрытая десятиминутка —
    `Failed`, следующая ещё не начата) до явного вызова
    `ConfirmReadyToContinue` — см. ниже. Такое закрытие **никогда** само по
    себе не завершает рабочий этап интервала (даже если это, скажем, седьмая
    десятиминутка подряд) — завершает его исключительно 5-я **успешная**.
- `SubmitFailureReason(check_id, reason: String)` — дописывает `reason` в уже
  закрытую десятиминутку со статусом `NoResponse` и пустым `reason` (SPEC.md
  п.2, сценарий "тишина"): пользователь наконец откликнулся и объяснил, что
  случилось. Не меняет `ended_at`/`status` этой строки — только `reason`. Это
  единственный use case, разрешающий изменение уже закрытой `TenMinCheck`.
  Ошибка, если строка не найдена, уже закрыта не как `NoResponse`, или `reason`
  уже был проставлен ранее.
- `ConfirmReadyToContinue(interval_id)` — реакция на "готов продолжить?" после
  провала рабочей десятиминутки (SPEC.md п.2: и для явного "нет" после ответа
  на "что случилось", и для "тишины" после `SubmitFailureReason`, и даже до
  него — пользователь может подтвердить готовность продолжить, не дожидаясь
  отдельного вопроса, если `reason` уже известен из явного "нет"). Применимо
  после **любого** провала, а не только "не последнего" — провальное закрытие
  само по себе никогда не завершает рабочий этап интервала (см.
  `SubmitTenMinAnswer` выше), поэтому продолжение всегда нужно. Создаёт новую
  `TenMinCheck` для следующего слота (`task_id` — текущая активная задача,
  `started_at = now`). Ошибка, если последняя десятиминутка интервала не
  является закрытой `Failed`/`NoResponse` (то есть подтверждать нечего — либо
  уже идёт новая десятиминутка, либо интервал принудительно завершён).
- `MarkReturnedFromRest(interval_id)` — явное действие пользователя (например,
  кнопка "Вернулся"), закрывает открытую десятиминутку **отдыха**:
  `ended_at = now` — независимо от того, уложился пользователь в номинальные
  10 минут или нет (переработка фиксируется как есть, без статуса "провалено"
  и без `reason`, см. SPEC.md п.2, п.4). Ошибка, если открытой десятиминутки
  отдыха нет.
- `AdvanceOpenTenMinChecks()` — **не вызывается планировщиком, а вызывается
  периодическим poll-циклом** (Задача 10) на каждом тике. Реализация:
  запросить все открытые `TenMinCheck` (`TenMinCheckRepository::find_open()`
  из Задачи 3); для каждой по числу и статусам уже закрытых десятиминуток того
  же интервала определить `is_rest` (см. `HourIntervalState` из Задачи 2) и
  посчитать `elapsed_since_start = Clock.now() - started_at`:
  - если это **рабочая** десятиминутка — передать
    `(elapsed_since_start, already_prompted = last_reminder_at.is_some())` в
    `WorkSlotPollDecision` из Задачи 2:
    - `NoActionYet` → ничего не делать;
    - `AskAreYouWorking` → `Notifier.send("Ты работаешь?")`,
      `last_reminder_at = now`. При стандартном 60-секундном шаге поллера
      (Задача 10) окно, в котором `WorkSlotPollDecision` возвращает этот
      исход, по ширине совпадает с шагом тика — вопрос практически всегда
      уходит ровно один раз; намеренно не дедуплицируется отдельным полем —
      редкое дублирование при дрожании тика не влияет на сохранённые данные
      и не считается багом;
    - `ResolveNoResponse` → закрыть **немедленно**: `ended_at = started_at +
      10мин`, `status = NoResponse`, `reason = None`, `last_reminder_at =
      None` (сбрасывается — счётчик для следующего расписания напоминаний,
      см. `RemindAwaitingResume` ниже, стартует заново от момента закрытия).
      Никакая новая десятиминутка не создаётся здесь — как и явное "нет" в
      `SubmitTenMinAnswer`, это состояние "жду возврата", разрешается только
      через `ConfirmReadyToContinue`. Важно: `ResolveNoResponse` **не может**
      завершить рабочий этап интервала, даже если это по счёту 5-я, 6-я и т.д.
      десятиминутка — рабочий этап завершает исключительно 5-я **успешная**
      (`Worked`), а `ResolveNoResponse` по определению производит только
      `NoResponse` (см. `SubmitTenMinAnswer` выше);
  - если это десятиминутка **отдыха** и `elapsed_since_start >= 10 мин` —
    передать `(elapsed_since_last_reminder, elapsed_since_wait_started =
    elapsed_since_start - 10 мин, burst/steady-конфиг)` в
    `ReminderScheduleDecision` из Задачи 2; если функция вернула `true` —
    `Notifier.send("Перерыв затянулся, ты вернулся?")`,
    `last_reminder_at = now`.
  Никакого `Scheduler`/`JobId`/`cancel` в реализации нет и не нужно — вся
  "отмена" сводится к тому, что закрытая (`ended_at IS NOT NULL`) десятиминутка
  просто перестаёт попадать в `find_open()` на следующем тике.
- `RemindAwaitingResume()` — тоже вызывается периодическим poll-циклом на
  каждом тике, параллельно с `AdvanceOpenTenMinChecks()`. Реализация:
  запросить `TenMinCheckRepository::find_awaiting_resume()` из Задачи 3
  (закрытые `Failed`/`NoResponse` десятиминутки, последние в ещё не закрытом
  интервале, следующая не начата); для каждой посчитать
  `elapsed_since_wait_started = Clock.now() - ended_at` и
  `elapsed_since_last_reminder = Clock.now() - (last_reminder_at ИЛИ ended_at)`
  и передать в `ReminderScheduleDecision`; если `true` —
  `Notifier.send(...)` (текст зависит от того, заполнен ли уже `reason`: если
  пуст — "Что случилось, почему не отвечаешь?", если уже заполнен —
  "Готов продолжить?"), `last_reminder_at = now`. Как только по этой строке
  вызван `ConfirmReadyToContinue` — она перестаёт попадать в выборку на
  следующем тике (интервал больше не "ждёт возврата").
- `SwitchTaskMidInterval(interval_id, new_task_id)` — реализация правила
  "задача готова" из SPEC.md: закрывает текущую задачу (`MarkTaskDone` из
  Задачи 6), переводит новую задачу в `in_progress`; оставшиеся (ещё не
  начавшиеся) десятиминутки этого часа создаются уже с `task_id = new_task_id`.
  Десятиминутка, уже находящаяся в процессе на момент вызова (её `ended_at`
  ещё `NULL`), НЕ прерывается и НЕ меняет `task_id` задним числом — она
  продолжает как обычно попадать в `find_open()`/`AdvanceOpenTenMinChecks` и
  завершается под прежней задачей естественным образом; специальной логики
  отмены здесь не требуется, потому что отменять нечего — нет отдельного
  запланированного job'а на текущую десятиминутку.
- `FinishHourInterval(interval_id, summary: String)` — закрывает интервал
  (`ended_at = now`), считает `successful_count` (при обычном, не
  принудительном завершении — всегда 5), сохраняет `summary` (обязательный
  ответ "что делали за этот час") в `hour_intervals.summary`, вызывает
  Notifier с итогом интервала. Вызывается адаптером после того, как рабочий
  этап интервала исчерпан (набрано 5 **успешных** десятиминуток — неважно,
  сколько при этом было провальных попыток — и отдых после них закрыт через
  `MarkReturnedFromRest`) и пользователь ответил на обязательный вопрос.

**Тестирование:**
- Сценарные тесты (given/when/then) на моках: полный happy path без провалов
  (ровно 5 десятиминуток, все `Worked`) → отдых засчитан; сценарий с
  провалами (например, 2 `Failed` вперемешку с 5 `Worked`, всего 7
  десятиминуток) → рабочий этап всё равно завершается ровно на 5-й
  **успешной**, отдых засчитан как обычно, а не отменяется из-за провалов;
  сценарий принудительного завершения интервала (`/finish_day` посреди
  работы, до 5 успешных, см. Задачу 8) → `successful_count < 5`, отдых не
  начисляется; сценарий "нет ответа" → ровно одна проваленная десятиминутка
  (никакого каскада на 2), не занимает место одной из 5 нужных успешных, час
  не сбрасывается, уже закрытые `Worked` сохранены; поздний отклик через
  `SubmitFailureReason` дописывает `reason` в уже закрытую строку, не трогая
  `ended_at`/`status`; после него `ConfirmReadyToContinue` создаёт новую
  десятиминутку с `started_at`, равным моменту подтверждения (а не моменту
  закрытия предыдущей); переработанный отдых — `MarkReturnedFromRest`
  фиксирует фактическую длительность (например, 30 минут вместо 10), это не
  влияет на `successful_count` и не требует `reason`; смена задачи
  посередине — каждый `TenMinCheck` после переключения имеет новый `task_id`.
- Тесты на `AdvanceOpenTenMinChecks` с фейковым `Clock` (единичные вызовы с
  заданным `elapsed`, без реального ожидания): рабочая десятиминутка на 9-й
  минуте → `NoActionYet`; на 10-й → `AskAreYouWorking`, `last_reminder_at`
  проставлен; без ответа на следующем тике → `ResolveNoResponse`, десятиминутка
  закрыта `NoResponse` немедленно (`ended_at ≈ started_at + 10 мин`, не позже),
  `reason = None`, `last_reminder_at` сброшен в `None`, новая десятиминутка **не
  создаётся** этим вызовом; десятиминутка отдыха на 9-й минуте своего таймера →
  `NoActionYet`; после 10-й минуты без возврата → напоминания по расписанию
  `ReminderScheduleDecision` (первое — сразу по достижении 10 минут, дальше —
  по `burst`/`steady` порогам), десятиминутка остаётся открытой сколь угодно
  долго до `MarkReturnedFromRest`.
- Тесты на `RemindAwaitingResume` с фейковым `Clock`: закрытая `NoResponse`
  десятиминутка без `reason`, интервал ещё не закрыт, следующая не начата →
  напоминания по тому же `burst`/`steady`-расписанию; после
  `ConfirmReadyToContinue` (создающего следующую десятиминутку) эта же строка
  больше не попадает в `find_awaiting_resume()` и напоминания прекращаются.

**Критерии приёмки:**
- Все сценарии из SPEC.md п.2 покрыты сценарными тестами.
- Ни один тест не спит реальное время (используется фейковый `Clock`).

## Задача 8. Application: use cases обеда и завершения дня

**Зависит от:** Задача 7.

**Цель:** обед и закрытие дня с проверкой нормы часов.

**Что реализовать:**
- `StartLunch(work_day_id)` / `EndLunch(work_day_id)` — фиксируют start/end,
  можно вызвать только между интервалами (не во время активного интервала).
- `SuggestLunchAfterNthInterval` — вспомогательная логика/событие (бот сам
  предлагает после 4-го интервала) — как доменное правило + вызов Notifier.
- `FinishWorkDay(work_day_id)` — закрывает день, считает итог (сколько из 8
  часовых интервалов закрыто, суммарное время по задачам, обеденное время
  отдельной строкой). Если на момент вызова есть активный незакрытый часовой
  интервал — он принудительно закрывается тем же путём, что и `FinishHourInterval`
  из Задачи 7, но без обязательного `summary` (пустой/`None`, вопрос "что делали
  за этот час" не блокирует завершение): `successful_count` считается по уже
  фактически произошедшим `TenMinCheck`, ещё не начавшиеся десятиминутки не
  создаются задним числом. Три возможных состояния незакрытого интервала на
  момент вызова (все три после ремедиации Задачи 1/7 из-за пересмотра раздела 2
  SPEC.md — без каскадов и без "восстановительных" сущностей):
  - есть открытая **рабочая** `TenMinCheck` (таймер идёт или бот ждёт ответа на
    "работаешь?") — принудительно закрывается: `ended_at = now`,
    `status = NoResponse`, `reason = None` (в отличие от обычного
    `WorkSlotPollDecision`, здесь длительность — фактическая, `now - started_at`,
    а не номинальные 10 минут, потому что дальнейшего ожидания уже не будет);
  - есть открытая десятиминутка **отдыха** — закрывается тем же путём, что и
    `MarkReturnedFromRest` из Задачи 7: `ended_at = now`, фактическая
    длительность фиксируется как есть, без `reason`;
  - последняя десятиминутка интервала уже **закрыта** (`Failed`/`NoResponse`,
    состояние "жду возврата" из `find_awaiting_resume()`) — ничего закрывать не
    нужно, она уже закрыта; интервал просто завершается без создания следующего
    слота.
  Отдельно отменять что-либо не требуется — как только `ended_at` интервала и
  его открытых `TenMinCheck` проставлены, они перестают попадать в
  `find_open()`/`find_awaiting_resume()` и больше не обрабатываются поллером
  (Задача 7/10).
- `PromptContinueIfIdle()` — **не вызывается планировщиком, а вызывается
  периодическим poll-циклом** (Задача 10) на каждом тике, аналогично
  `AdvanceOpenTenMinChecks` из Задачи 7. Реализация: запросить все открытые
  `work_days` без активного интервала
  (`WorkDayRepository::find_open_without_active_interval()` из Задачи 3); для
  каждого посчитать `elapsed = Clock.now() - (last_idle_prompt_at ИЛИ момент
  начала простоя — окончание последнего интервала/обеда/старт дня, смотря что
  позже)` и передать в чистую функцию `IdlePromptDecision` из Задачи 2 вместе
  с порогом `N` часов; если она вернула `true` — `Notifier.send("Готовы
  продолжить работу?")` и `work_days.last_idle_prompt_at = now`. Отдельной
  "отмены" не требуется: как только пользователь стартует интервал
  (`StartHourInterval`) — `work_day` перестаёт попадать в
  `find_open_without_active_interval()` и напоминания сами прекращаются на
  следующем тике; аналогично при `FinishWorkDay`. Автоматического завершения
  дня по таймауту нет — только периодическое напоминание.

**Тестирование:**
- Тест: обед нельзя начать во время активного незакрытого интервала (бизнес-ошибка).
- Тест: `FinishWorkDay` корректно исключает обеденное время из 8-часовой нормы.
- Тест: `FinishWorkDay`, вызванный во время активного интервала (например,
  после 2 успешных десятиминуток из нужных 5), принудительно закрывает
  интервал с `successful_count = 2`, не запускает дальнейшие попытки, отдых не
  начисляется (успешных меньше 5).
- Тест: `FinishWorkDay` во всех трёх состояниях незакрытого интервала —
  открытая рабочая десятиминутка (закрывается `NoResponse` с фактической, не
  номинальной, длительностью), открытый отдых (закрывается с фактической
  длительностью, без `reason`), уже закрытая "жду возврата" (ничего не
  закрывается повторно) — во всех трёх день корректно завершается без
  зависших таймеров.
- Тест: автопредложение обеда триггерится ровно после 4-го закрытого интервала,
  не раньше и не позже.
- Тест: `PromptContinueIfIdle` не выбирает `work_day` с активным часовым
  интервалом (не попадает в `find_open_without_active_interval()`).
- Тест на `IdlePromptDecision`/`PromptContinueIfIdle` с фейковым `Clock`:
  `elapsed < N часов` → `Notifier` не вызывается, `last_idle_prompt_at` не
  меняется; `elapsed >= N часов` → `Notifier` вызывается один раз за тик,
  `last_idle_prompt_at` обновляется на текущее время (следующий вызов сразу
  после этого снова возвращает `false`, пока не пройдёт ещё `N` часов).
- Тест: после `StartHourInterval` или `FinishWorkDay` соответствующий
  `work_day` перестаёт возвращаться `find_open_without_active_interval()`, и
  `PromptContinueIfIdle` больше не шлёт по нему напоминаний на следующих тиках
  (никакой отдельной операции "отмены" не вызывается — это следствие того, что
  запрос к БД просто больше не находит эту строку).

**Критерии приёмки:**
- Итоговые числа в `FinishWorkDay` сходятся с ручным расчётом на 2-3 заранее
  прописанных фикстурах-сценариях (golden test).
- Значение `N` (часы простоя до напоминания) читается из конфигурации, а не
  захардкожено (см. Задача 13).

## Задача 9. Application: отчёты и экспорт

**Зависит от:** Задача 8.

**Цель:** use cases для `/report` и экспорта в CSV.

**Что реализовать:**
- `BuildDayReport(work_day_id) -> ReportDto` — текстовое представление (время
  по задачам, провальные десятиминутки с причинами, обед, норма 8ч, а также
  `summary` каждого завершённого часового интервала — ответ на "что делали за
  этот час"). Если день ещё не закрыт и текущий часовой интервал не завершён —
  в отчёт попадают только уже завершённые десятиминутки этого интервала, сам
  интервал не считается "закрытым" для нормы 8 часов (см. SPEC.md п.5).
- `BuildPeriodReport(user_id, period: Week | Month, at: Option<NaiveDate>) -> ReportDto` —
  агрегированный отчёт за неделю/месяц: сумма отработанного времени и по
  задачам, число закрытых дней с выполненной нормой, суммарное обеденное время,
  по всем `work_days` пользователя, попадающим в период. Границы периода
  вычисляются по календарной дате `work_days.started_at`, сконвертированной из
  UTC в `users.timezone` (см. SPEC.md п.5) — не по UTC-дате. Если `at` не
  передан (команда без даты — обычный случай для `/report_week`/`/report_month`),
  "сегодня" вычисляется **внутри use case**, а не в Telegram-адаптере, как
  `Clock.now()` (порт из Задачи 3), сконвертированный в `users.timezone` — это
  бизнес-правило, а не забота адаптера, и должно жить в одном месте, иначе
  дублирование конвертации таймзоны разъедется между адаптерами. Использует тот
  же `ReportDto`, что и дневной отчёт (с полем периода).
- `ExportDayReportCsv(work_day_id) -> Vec<u8>` (CSV в памяти, отдаётся наружу
  через Notifier как `OutboundMessage::Document`, см. Задачу 3).
- `ReportDto`/CSV-формат — в `application`, без зависимости на конкретный формат
  вывода интерфейса (Telegram просто сериализует/отправляет).

**Тестирование:**
- Golden-тесты: фиксированный сценарий дня → сравнение с эталонной CSV-строкой
  и текстом отчёта (снапшот-тестирование).
- Golden-тест на `BuildPeriodReport`: фикстура из нескольких `work_days` внутри
  недели/месяца → сравнение агрегированных чисел с ручным расчётом; дни за
  пределами периода (с учётом таймзоны пользователя) не должны попадать в
  сумму (граничные даты периода).
- Тест: `BuildPeriodReport` без явного `at` для пользователя в часовом поясе
  восточнее UTC (например `UTC+7`), когда фейковый `Clock.now()` близок к
  полуночи по UTC, но уже следующий локальный день — период считается по
  локальной дате, а не по UTC-дате `Clock.now()`.

**Критерии приёмки:**
- CSV открывается в Excel/LibreOffice без искажений (проверить кодировку UTF-8,
  разделители).
- `BuildPeriodReport` корректно работает на границах периода (первый/последний
  день недели или месяца, разные часовые пояса пользователя).

**✅ Выполнено (2026-08-22):** `ReportDto`/`Period`/`TaskTimeEntry`/
`FailedCheckEntry`/`DayReportInfo`/`PeriodReportInfo` — в
`crates/application/src/report_dto.rs` (не привязаны к формату вывода;
`ReportDto::to_text()` — общий текстовый рендер для дневного и
периодического отчёта). `BuildDayReport`, `BuildPeriodReport`,
`ExportDayReportCsv` реализованы в `crates/application/src/use_cases`.
`BuildDayReport` переиспользует `classify_checks` из `support.rs`: время по
задачам и провальные десятиминутки берутся только из уже закрытых слотов
каждого интервала (в том числе ещё не завершённого — его самого при этом не
засчитывает в `closed_intervals`/норму 8ч), заголовки задач подтягиваются
через `TaskRepository`. `ExportDayReportCsv` переиспользует ту же приватную
`build_day_report_dto(...)` (без дублирования логики) и сериализует
`ReportDto` в CSV вручную (RFC4180-экранирование, `\r\n`, UTF-8 BOM для
Excel) — без добавления зависимости на `csv`-крейт. `BuildPeriodReport`
считает границы периода (неделя — пн..вс, месяц — календарный) по

считается по локальной дате. `cargo test -p application` (90 тестов,
включая 10 новых для отчётов), `cargo test --workspace`,
`cargo build --workspace` и `cargo clippy --workspace --all-targets`
проходят чисто.

## Задача 10. Poll-цикл на tokio

**Зависит от:** Задача 7 и Задача 8 (нужны use cases `AdvanceOpenTenMinChecks`,
`RemindAwaitingResume` и `PromptContinueIfIdle`), может делаться параллельно с
Задачами 5–9 в части каркаса цикла, но по-настоящему протестирована будет
только после них; нужна перед Задачей 13.

**Цель:** вместо отдельного `Scheduler`-порта с job'ами (сознательно убран из
Задачи 3, см. SPEC.md п.4 — "таймер = пара UTC-полей, а не запланированное
задание") — простой периодический цикл на `tokio::time::interval`, который
каждый тик вызывает use cases из Задачи 7 и 8. Это единственный механизм
проактивных сообщений во всей системе.

**Что реализовать:**
- `PollLoop` — `tokio::time::interval(poll_interval)` (конфигурируемый, по
  умолчанию 60 секунд — совпадает с минимальной частотой `burst_interval` из
  расписания напоминаний, см. SPEC.md раздел 7 и Задачу 7), на каждом тике
  вызывает `AdvanceOpenTenMinChecks()`, `RemindAwaitingResume()` и
  `PromptContinueIfIdle()` (порядок между ними не важен, это разные сущности,
  можно последовательно или параллельно).
- Никакого состояния между тиками цикл не хранит (ни `HashMap`, ни `JobId`) —
  вся нужная информация каждый раз перечитывается из БД через репозитории.
  Это делает цикл тривиально restart-safe: после рестарта процесса первый же
  тик отработает как обычно, просто увидит текущее состояние БД.

**Тестирование:**
- Тесты с `tokio::time::pause()`/`advance()` (виртуальное время) — не ждать
  реальные секунды в тестах: продвинуть время на несколько тиков вперёд и
  проверить, что use cases были вызваны ожидаемое число раз.
- Тест: `PollLoop`, запущенный заново на тех же данных БД (эмулирует рестарт
  процесса — просто новый экземпляр `PollLoop` без предыдущего состояния),
  ведёт себя идентично работающему без перерыва циклу — подтверждает
  restart-safety на уровне этого адаптера.

**Критерии приёмки:**
- Полный прогон нескольких тиков в тесте занимает <1 секунды реального времени
  благодаря паузе времени tokio.
- Реализация `PollLoop` укладывается в ~30-50 строк — никакой отдельной
  структуры данных для хранения "активных задач" не требуется (в отличие от
  прежнего `TokioScheduler`/`HashMap<JobId, JoinHandle>`).

## Задача 11. Telegram-адаптер: входящие команды → use cases

  `MarkReturnedFromRest` из Задачи 7 — разные use cases за одинаковой по смыслу

- Middleware/первый шаг любого апдейта — вызов `RegisterUserIfNotExists`.
- Маппинг `teloxide::types::ChatId` ↔ `TelegramId` из domain — только в этом
  адаптере.

**Тестирование:**
- Unit-тесты на функции-парсеры апдейтов (апдейт → вызов какого use case с
  какими аргументами) без реального Telegram API — через фейковый `Bot`/mock
  запросов teloxide, либо структурируя код так, чтобы "разбор апдейта" была
  чистая функция, тестируемая без сети.
- Ручной acceptance-тест (описать в этой задаче сценарий): пройти весь день от
  `/start_day` до `/finish_day` в тестовом боте.

**Критерии приёмки:**
- Крейт `adapters/telegram` зависит от `application`, но `application` не
  зависит от `adapters/telegram` (проверяется по графу зависимостей Cargo).
- Ни одного прямого вызова `TaskRepository`/других репозиториев в обход
  use cases (проверяется по импортам крейта).
- Все тексты сообщений вынесены в один модуль (легко менять формулировки).

  Никакого отдельного шага восстановления состояния при старте не требуется —
  это прямое следствие принципа из SPEC.md п.4 (таймер — это просто пара
  UTC-полей в БД, а не запись в памяти процесса): первый же тик `PollLoop`
  после старта видит текущее состояние БД и ведёт себя одинаково что после
  холодного старта, что после рестарта посреди дня.
- Graceful shutdown (Ctrl+C останавливает `PollLoop` и закрывает БД-пул).

**Тестирование:**
- Тест запуска: приложение стартует с тестовым конфигом и падает с понятной
  ошибкой при отсутствии обязательных переменных окружения.
- Интеграционный тест restart-safety на tempfile SQLite: создать открытый
  `work_day` с активным интервалом и незавершённой десятиминуткой напрямую
  через репозитории (эмулируя состояние "как будто процесс уже работал и упал"),
  затем поднять composition root с нуля (как при реальном рестарте) и
  убедиться, что ближайший тик `PollLoop` обрабатывает эту десятиминутку
  корректно — без какого-либо специального кода восстановления.

**Критерии приёмки:**
- `cargo run -p app` поднимает бота при валидном `.env`.
- Нет `unwrap()`/`expect()` на пользовательском вводе или сетевых вызовах вне
  явно задокументированных мест инициализации.

## Задача 14. End-to-end сценарии и приёмочное тестирование MVP

**Зависит от:** Задача 13 (всё собрано).

**Цель:** зафиксировать и прогнать полный набор приёмочных сценариев из
SPEC.md как воспроизводимые тесты (по возможности — end-to-end через
application-слой с реальной SQLite tempfile, mock-Notifier и фейковым `Clock`
с управляемым временем — никакого mock-планировщика не требуется, т.к.
таймеры полностью выражены через данные в БД; чисто через Telegram — вручную
по чек-листу).

**Сценарии (минимум):**
1. Регистрация нового пользователя первым любым сообщением.
2. Полный рабочий день: 8 интервалов, все 5/5 — отдых считается, норма 8ч выполнена.
3. Интервал с провалами, но без принудительного завершения дня — например,
   2 провальные десятиминутки вперемешку с успешными (итого 7 десятиминуток на
   интервал вместо 5) — рабочий этап всё равно завершается на 5-й **успешной**,
   отдых начисляется как обычно, в задачу идёт 50 мин работы + 10 мин отдыха,
   а фактическая длительность интервала (`ended_at - started_at`) заметно
   больше номинальных 60 минут — этот перерасход виден в отчёте (см. сценарий
   16). Провал не отменяет отдых и не занимает место одной из 5 нужных
   успешных десятиминуток.
4. Сценарий "нет ответа" на рабочей десятиминутке — проваливает ровно **один**
   слот (`NoResponse`, `reason = None`, длительность номинальная), час не
   сбрасывается (уже набранные `Worked` сохранены); пользователь откликается
   позже — `reason` дописывается в уже закрытую десятиминутку
   (`SubmitFailureReason`), затем "готов продолжить?" → `ConfirmReadyToContinue`
   стартует новую десятиминутку с `started_at`, равным моменту подтверждения
   (не моменту исходного закрытия) — никакого каскада на 2 слота.
5. Переработанный отдых: после 5/5 пользователь не откликается на "отдыхай 10
   минут" вовремя — десятиминутка отдыха остаётся открытой, бот напоминает по
   расписанию (`burst`/`steady`), фактическая длительность (например, 30 минут
   вместо 10) фиксируется по `MarkReturnedFromRest`; это не влияет на
   `successful_count` интервала и не помечается как провал.
6. Смена задачи посередине интервала — время корректно разбито между двумя
   задачами (через `task_id` на отдельных `TenMinCheck`).
7. Обед вручную посреди дня + обед по предложению после 4-го интервала.
8. `/report` в середине дня (включая незавершённый интервал) и `/finish_day` —
   числа совпадают.
9. Экспорт CSV — сверка вручную, отправляется как документ (не текстом).
10. День начат, интервал не стартован дольше `N` часов — приходит периодическое
    напоминание "Готовы продолжить работу?"; после старта интервала повторные
    напоминания прекращаются; день не завершается автоматически.
11. `/report_week` / `/report_month` за период с несколькими рабочими днями —
    агрегированные числа совпадают с ручным расчётом по исходным дням, с учётом
    таймзоны пользователя на границах периода.
12. Задача с приоритетом и дедлайном корректно сохраняется/отображается в пуле
    задач.
13. Создание/редактирование задачи через бота (`CreateTask`/`UpdateTask` из
    Задачи 6) и корректная сортировка/фильтрация пула задач (`ListAvailableTasks`)
    по приоритету и дедлайну.
14. `/finish_day` во время активного часового интервала — проверяется во всех
    трёх состояниях незакрытого интервала (открытая рабочая десятиминутка,
    открытый отдых, уже закрытая "жду возврата"; см. Задачу 8): интервал
    закрывается по фактическим десятиминуткам, отдых не начисляется, если не
    было 5/5, день корректно завершается без зависших таймеров.
15. Рестарт процесса с открытым днём: активный интервал с незавершённой
    (открытой) десятиминуткой, либо с последней десятиминуткой, закрытой как
    провал и ожидающей возврата пользователя, либо день без активного
    интервала — после перезапуска напоминания (`AdvanceOpenTenMinChecks`,
    `RemindAwaitingResume`, `PromptContinueIfIdle`, смотря какое из состояний)
    продолжают приходить без какого-либо специального кода восстановления,
    просто потому что `PollLoop` (Задача 10) каждый тик заново читает
    состояние из БД (см. SPEC.md п.4).
16. Отчёт "план vs факт по времени" (SPEC.md раздел 5): день с несколькими
    провалами и одним переработанным отдыхом → сумма перерасхода по всем
    интервалам сходится с ручным расчётом (номинальные 8×1ч против фактической
    суммы `ended_at - started_at` по каждому интервалу).

**Критерии приёмки MVP:**
- Все 16 сценариев проходят как автотесты (или задокументированы как ручной
  чек-лист с результатом, если e2e через Telegram недостижим в CI).
- `README.md` в корне репозитория обновлён: как запустить, архитектура,
  ссылка на SPEC.md и этот файл.
- Итог: рабочая первая версия бота, доступная через Telegram, данные переживают
  перезапуск процесса (SQLite-файл персистентен).
