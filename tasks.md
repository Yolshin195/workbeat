# workbeat — план реализации (гексагональная архитектура)

Задачи идут строго по цепочке: каждая следующая опирается на результат предыдущей.
Внутри каждой задачи — что сделать, как тестировать, критерии приёмки. Делать
можно по одной, сохраняя контекст только текущей задачи и этого документа.

## Общая архитектура (ориентир для всех задач)

```
crates/
  domain/          — сущности, value objects, бизнес-правила (0 внешних зависимостей)
  application/      — use cases + порты (traits), зависит только от domain
  adapters/
    persistence-sqlite/  — реализация репозиториев (sqlx/rusqlite)
    scheduler-tokio/     — периодический poll-цикл (проверяет истёкшие таймеры в БД)
    telegram/             — teloxide-адаптер: входящие апдейты → use cases,
                            исходящие сообщения ← Notifier
  bin/app/          — composition root: собирает адаптеры + application, конфиг, запуск
```

Правило на все задачи: **domain** не знает про SQLite/Telegram/tokio-время.
**application** знает только про traits (порты), не про конкретные реализации.
Адаптеры реализуют порты и ничего не знают друг о друге.

## Задача 1. Каркас workspace и доменные сущности

**Цель:** создать Cargo workspace с крейтами `domain`, `application`,
`adapters/*` (пустые), `bin/app`. В `domain` — структуры и value objects из
SPEC.md раздела 6, без бизнес-логики переходов состояний, только сами типы.

**Что реализовать:**
- Value objects: `TelegramId`, `UtcTimestamp` (обёртка над `chrono::DateTime<Utc>`),
  `TimeZoneOffset`.
- Сущности: `User`, `Task` (+ `TaskStatus` enum: Ready/NotReady/InProgress/Done,
  + опциональный `TaskPriority` enum: High/Medium/Low, + опциональный
  `deadline: Option<NaiveDate>`), `WorkDay` (+ `last_idle_prompt_at: Option<UtcTimestamp>`
  — см. принцип таймеров в SPEC.md п.4), `HourInterval` (+ `summary: Option<String>`
  — ответ на обязательный вопрос "что делали за этот час"), `TenMinCheck`
  (+ `task_id: TaskId` — задача, активная в момент этой десятиминутки,
  + `is_recovery: bool` — обычная десятиминутка или восстановительная
  (ежеминутный опрос при молчании), см. SPEC.md п.6, + `CheckStatus` enum:
  Worked/Failed/NoResponse).
- Все поля — как в схеме SQLite из SPEC.md, но как rust-типы (не строки для времени/enum).
  Важно: `task_id` живёт на `TenMinCheck`, а не на `HourInterval` — один часовой
  интервал может включать десятиминутки разных задач (правило "задача готова").
  Важно (принцип таймеров, SPEC.md п.4): у всех сущностей с длительностью
  (`WorkDay`, `HourInterval`, `TenMinCheck`) время хранится строго как пара
  `started_at`/`ended_at: Option<UtcTimestamp>` — никаких отдельных типов
  "таймер"/"job" в domain нет и не будет; "истекло ли время" — это всегда
  чистая функция от `now` и `started_at` (см. Задачу 2), а не что-то, что
  само себя планирует.
- Никаких `impl` с бизнес-логикой — только конструкторы и геттеры.

**Тестирование:**
- Unit-тесты на конструкторы: невалидные значения (например `successful_count > 5`)
  должны быть невозможны на уровне типов или возвращать `Result`.
- `cargo test -p domain` проходит без сети/файловой системы.

**Критерии приёмки:**
- `cargo build --workspace` собирается.
- `domain` не имеет зависимостей на tokio/sqlx/teloxide в `Cargo.toml`.
- Есть `README.md` в `domain/` с описанием сущностей.

**⚠️ Ремедиация (эта задача уже реализована по устаревшей схеме):** текущий код
`crates/domain/src/hour_interval.rs` и `ten_min_check.rs` соответствует версии
схемы ДО ревизий SPEC.md п.6 от 2026-08-21 — `task_id` был на `HourInterval`, а
`summary` отсутствовал. Схема была пересмотрена, потому что она делала
физически невозможным сохранение сценария "смена задачи посередине часа"
(Задача 2/Задача 7 тестируют его на чистых функциях, но в SQLite его негде было
хранить). Перед началом Задачи 2 нужно:
- убрать `task_id: TaskId` из `HourInterval`, добавить `summary: Option<String>`;
- добавить `task_id: TaskId` и `is_recovery: bool` в `TenMinCheck`;
- добавить `last_idle_prompt_at: Option<UtcTimestamp>` в `WorkDay`;
- обновить конструкторы и существующие unit-тесты всех затронутых структур.

## Задача 2. Доменные бизнес-правила (чистые функции, без портов)

**Зависит от:** Задача 1.

**Цель:** реализовать в `domain` чистую логику переходов состояний часового
интервала и десятиминуток — без ввода-вывода, только функции
`(текущее состояние, событие) -> новое состояние`.

**Что реализовать:**
- `TenMinCheckPollDecision`: **чистая функция** `(is_recovery: bool, elapsed: Duration,
  status: Option<CheckStatus>) -> PollOutcome`, где `PollOutcome` — одно из:
  `NoActionYet` / `AskAreYouWorking` (спросить "работаешь?" один раз) /
  `RemindWhySilent` (повторить "почему не отвечаешь?") /
  `ResolveNoResponse` (закрыть как `NoResponse` и, если это обычная
  десятиминутка — дать сигнал создать восстановительную). Это единственное
  место, где решается "что делать по истечении времени" — она не знает про
  `Clock`/БД/Notifier, только считает по переданному `elapsed`. Пороговые
  константы (10 минут на обычную десятиминутку, повтор раз в минуту для
  восстановительной) живут здесь же. Именно эта функция будет вызываться
  application-слоем на каждом poll-тике (см. Задачу 3/7) — таким образом даже
  логика "истёк ли таймер" остаётся чистой и тестируется без tokio/времени.
- `TenMinCheckState`: машина состояний для одной десятиминутки
  (Pending → Worked | Failed | NoResponseFailed) по правилам из SPEC.md п.2.
  Явно учесть: ответ, полученный в любой момент восстановительной десятиминутки
  (ежеминутный опрос "почему не отвечаешь"), останавливает дальнейшую эскалацию,
  но не меняет итоговый статус — обе десятиминутки (исходная и восстановительная)
  остаются `Failed`/`NoResponse`, и текст ответа записывается как `reason` **в
  обе** десятиминутки (это одно и то же объяснение простоя на оба слота).
- `IdlePromptDecision`: аналогичная чистая функция `(elapsed_since_last_prompt: Duration,
  idle_threshold: Duration) -> bool` для `PromptContinueIfIdle` — та же логика
  "elapsed ≥ порог", просто с другим порогом (`N` часов) и другой точкой отсчёта
  (`last_idle_prompt_at`, см. SPEC.md п.6).
- `HourIntervalState`: агрегирует 5 десятиминуток → считает `successful_count`,
  решает, положен ли отдых (только при 5/5).
- Функция расчёта времени задачи: сумма успешных десятиминуток + (отдых, если 5/5),
  по всем интервалам, привязанным к задаче.
- Функция определения дневной нормы: сколько из 8 часовых интервалов закрыто.

**Тестирование (обязательно табличные/parametrized тесты):**
- `TenMinCheckPollDecision`: табличный тест по всем комбинациям
  `is_recovery`/`elapsed`/`status` — например, обычная десятиминутка с
  `elapsed = 9 мин` → `NoActionYet`, `elapsed = 10 мин` → `AskAreYouWorking`,
  `elapsed = 11 мин` без ответа → `ResolveNoResponse`; восстановительная с
  `elapsed = 3 мин` → `RemindWhySilent`, `elapsed = 10 мин` → `ResolveNoResponse`.
- `IdlePromptDecision`: `elapsed_since_last_prompt < N часов` → `false`,
  `>= N часов` → `true`.
- Все комбинации 0/5..5/5 успешных десятиминуток → корректный расчёт времени
  задачи и признака "положен отдых".
- Сценарий "нет ответа" → корректно проваливает именно 2 десятиминутки, как
  описано в SPEC.md; отдельный тест на ответ внутри восстановительного окна —
  статус всё равно проваленный.
- Сценарий смены задачи посередине часа (после 2-й из 5) → время корректно
  разбивается между двумя задачами (после ремедиации Задачи 1 это моделируется
  через `task_id` на каждом отдельном `TenMinCheck`, а не на `HourInterval`).
- Property-based тест (например `proptest`) на инвариант: сумма времени по
  задачам в рамках интервала никогда не превышает 60 минут.

**Критерии приёмки:**
- 100% покрытие бизнес-правил юнит-тестами (без моков, чистые функции).
- Ни один тест не требует async/tokio.

## Задача 3. Порты (traits) в application

**Зависит от:** Задача 2.

**Цель:** описать в `application` все интерфейсы, через которые use cases будут
общаться с внешним миром — ещё без реализаций.

**Что реализовать (traits):**
- `UserRepository`, `TaskRepository`, `WorkDayRepository`, `HourIntervalRepository`,
  `TenMinCheckRepository` — CRUD/query методы, все `async_trait`, возвращают
  `Result<_, RepoError>`. Отдельно предусмотреть query-методы, нужные для
  периодического опроса (poll, см. Задачу 7/8/10) — единственного механизма
  проактивных сообщений в системе (SPEC.md п.4: никакого отдельного
  планировщика/job'ов нет, всё через "начался ли таймер и сколько прошло"):
  - `WorkDayRepository::find_open_without_active_interval()` — открытые
    `work_days` (`finished_at IS NULL`), у которых сейчас нет незакрытого
    `HourInterval` (кандидаты на `PromptContinueIfIdle`);
  - `TenMinCheckRepository::find_open()` — все `TenMinCheck` с `ended_at IS NULL`
    по всем активным интервалам (кандидаты на opros "работаешь?"/"почему не
    отвечаешь?").
  Обе нужны периодическому поллеру и одинаково исправно работают что на первом
  тике после старта процесса, что после рестарта — они просто читают текущее
  состояние из БД, никакого отдельного шага восстановления не требуется.
- `Clock` — `fn now(&self) -> UtcTimestamp` (для тестируемости времени). Это
  **единственный** порт, нужный use cases для работы со временем — никакого
  `Scheduler`/`JobId`/`schedule_once`/`cancel` в системе нет: вместо
  "запланировать job и не забыть отменить" вся проактивность реализована как
  периодический опрос (poll), считающий `now() - started_at` по данным из БД
  (см. SPEC.md п.4). Планировщика в application-порту действительно нет —
  цикл опроса (`tokio::time::interval`) целиком живёт в адаптере (Задача 10)
  и просто вызывает use cases каждый тик.
- `Notifier` (исходящий порт для интерфейсов) — `async fn send(&self, user: TelegramId, message: OutboundMessage)`.
  `OutboundMessage` — enum в domain или application, не привязан к Telegram
  (никаких `ChatId` из teloxide здесь). Обязательные варианты:
  `OutboundMessage::Text(String)` и
  `OutboundMessage::Document { filename: String, bytes: Vec<u8> }` (нужен для
  отправки CSV-экспорта из Задачи 9 как файла, а не текстом — без этого
  варианта Задача 12 не сможет реализовать отправку документа).

**Тестирование:**
- Для каждого порта — `mock`-реализация (через `mockall` или ручные фейки) в
  `application/src/testing.rs`, используемая последующими задачами.
- Компилируется без реализаций-адаптеров (только traits).

**Критерии приёмки:**
- `application` собирается, имея в зависимостях только `domain`, `async-trait`,
  `mockall` (dev-dependency), без sqlx/teloxide/tokio-runtime специфики (можно
  `tokio::time::Duration` как нейтральный тип, но не сам tokio runtime).

## Задача 4. SQLite-адаптер: миграции и репозитории

**Зависит от:** Задача 3.

**Цель:** реализовать все репозитории из Задачи 3 поверх SQLite (`sqlx` с
компилируемыми миграциями или `rusqlite`).

**Что реализовать:**
- SQL-миграции ровно по схеме из SPEC.md п.6 (актуальная ревизия: `task_id` и
  `is_recovery` — на `ten_min_checks`, а не на `hour_intervals`;
  `hour_intervals.summary` для ответа на "что делали за этот час";
  `work_days.last_idle_prompt_at`), включая колонки `priority`/`deadline` в
  `tasks` (оба NULL-able, без `NOT NULL`) и корректные объявленные типы для дат
  (`DATE` для `deadline`, `DATETIME` для остальных временных полей) (плюс
  индексы: по `user_id`, `work_day_id`, `hour_interval_id`, `ten_min_checks.task_id`,
  и частичные индексы на `ended_at IS NULL`/`finished_at IS NULL` там, где
  периодический опрос из Задачи 7/8/10 ищет "ещё не завершённые" строки —
  это самый частый запрос в системе, выполняется на каждом poll-тике).
- Реализация каждого `*Repository` trait из Задачи 3 в `adapters/persistence-sqlite`.
- Маппинг rust enum ↔ TEXT в БД (явные `TryFrom`/`From`, никаких "magic strings"
  в бизнес-коде).

**Тестирование:**
- Интеграционные тесты на **временной SQLite БД** (`:memory:` или tempfile) для
  каждого репозитория: create → read → update round-trip.
- Тест на миграции: применяются с нуля без ошибок.
- Тест конкурентного доступа (2 параллельных tokio-задачи пишут в разные
  таблицы) — SQLite не должен падать (проверить `busy_timeout`/WAL режим).

**Критерии приёмки:**
- `cargo test -p adapters-persistence-sqlite` проходит на чистой БД в CI без
  внешних сервисов.
- Файл БД создаётся по пути из конфига, схема соответствует SPEC.md.

## Задача 5. Application: use cases регистрации и старта дня

**Зависит от:** Задача 4 (но тестируется с моками из Задачи 3, реальная БД не нужна).

**Цель:** первые use cases, минимально достаточные для регистрации пользователя
и начала рабочего дня.

**Что реализовать:**
- `RegisterUserIfNotExists(telegram_id) -> User` — вызывается на любое входящее
  сообщение (идемпотентно).
- `StartWorkDay(user_id) -> WorkDay` — команда `/start_day`; ошибка, если день
  уже открыт.
- Каждый use case — отдельная структура с `execute()`, принимающая нужные порты
  через конструктор (dependency injection вручную, без DI-фреймворка).

**Тестирование:**
- Unit-тесты на моках репозиториев: happy path + edge cases (повторная
  регистрация — не дублирует; повторный `/start_day` в открытый день — ошибка
  бизнес-правила, а не паника).

**Критерии приёмки:**
- Use cases не импортируют ничего из `adapters/*` и не содержат SQL/Telegram-типов.
- Все ошибки — типизированные (`thiserror`), не `anyhow::Error` наружу из
  application (можно внутри адаптеров).

## Задача 6. Application: use cases управления задачами

**Зависит от:** Задача 5.

**Цель:** реализовать CRUD и переходы статусов сущности `Task` из SPEC.md
раздела 3. Без этой задачи Задача 7 (часовой интервал) не имеет способа
переключать `in_progress`/`done`, не обходя `TaskRepository` напрямую из
бизнес-логики, а Задача 11 (Telegram-адаптер) не сможет показывать/фильтровать
пул задач, не обращаясь к `TaskRepository` в обход `application` — что
нарушает архитектурное правило "use cases — единственная точка бизнес-логики".

**Что реализовать:**
- `CreateTask(user_id, title, priority: Option<TaskPriority>, deadline: Option<NaiveDate>) -> Task`
  — создаётся сразу в статусе `not_ready` или `ready` (на усмотрение параметра).
- `UpdateTask(task_id, title?, priority?, deadline?, status: Option<Ready|NotReady>)`
  — редактирование полей, задаваемых пользователем вручную; не позволяет
  выставить `in_progress`/`done` напрямую.
- `ListAvailableTasks(user_id, filter: Ready|NotReady|All) -> Vec<Task>` —
  список пула задач, отсортированный по приоритету (high → medium → low → без
  приоритета), затем по дедлайну (раньше — выше, без дедлайна — в конце).
- `MarkTaskInProgress(task_id)` / `MarkTaskDone(task_id)` — внутренние use
  cases, переиспользуемые Задачей 7 при старте интервала и по команде "задача
  готова"; не вызываются напрямую из Telegram-адаптера.

**Тестирование:**
- Unit-тесты на моках: сортировка пула по приоритету/дедлайну (табличный тест
  с несколькими комбинациями присутствия/отсутствия priority и deadline),
  фильтрация по статусу.
- Тест: `UpdateTask` не позволяет установить `in_progress`/`done` через
  пользовательское редактирование — только через `MarkTaskInProgress`/`MarkTaskDone`.

**Критерии приёмки:**
- Use cases не импортируют ничего из `adapters/*`.
- В Задаче 11 нет ни одного прямого вызова `TaskRepository` — только через use
  cases этой задачи.

## Задача 7. Application: use cases часового интервала и десятиминуток

**Зависит от:** Задача 6.

**Цель:** реализовать полный цикл часового интервала, используя бизнес-правила
из Задачи 2 и порты из Задачи 3.

**Что реализовать:**
- `StartHourInterval(work_day_id, task_id)` — старт только по явному действию
  пользователя, ошибка, если предыдущий интервал не закрыт; переводит задачу в
  `in_progress` через `MarkTaskInProgress` из Задачи 6.
- `SubmitTenMinAnswer(interval_id, answer: Yes|No, reason: Option<String>)` —
  создаёт `TenMinCheck` с `task_id`, равным текущей активной задаче интервала,
  и `is_recovery = false`. Закрывает открытую десятиминутку (`ended_at = now`,
  `status`), а если это была восстановительная (`is_recovery = true`) —
  дополнительно копирует `reason` в исходную (обычную) десятиминутку, которой
  она предшествовала (см. SPEC.md п.2), и всё равно оставляет статус обеих
  `Failed`/`NoResponse` (ответ во время восстановления не спасает статус).
- `AdvanceOpenTenMinChecks()` — **не вызывается планировщиком, а вызывается
  периодическим poll-циклом** (Задача 10) на каждом тике. Реализация:
  запросить все открытые `TenMinCheck` (`TenMinCheckRepository::find_open()`
  из Задачи 3), для каждого посчитать `elapsed = Clock.now() - started_at` и
  передать `(is_recovery, elapsed, status)` в чистую функцию
  `TenMinCheckPollDecision` из Задачи 2; по результату:
  - `AskAreYouWorking` → `Notifier.send("Ты работаешь?")`. При стандартном
    60-секундном шаге поллера (Задача 10) окно `[10, 11)` минут, в котором
    `TenMinCheckPollDecision` возвращает этот исход, по ширине совпадает с
    шагом тика — вопрос практически всегда уходит ровно один раз. Специально
    дедуплицировать повторную отправку не требуется: намеренно принятое
    упрощение (без лишнего поля-флага) — в редком случае дрожания тика
    сообщение может уйти дважды, это не влияет на сохранённые данные
    (десятиминутка всё равно закрывается по тем же правилам) и не считается
    багом;
  - `RemindWhySilent` → `Notifier.send("Что случилось, почему не отвечаешь?")`;
  - `ResolveNoResponse` на обычной десятиминутке → закрыть её как `NoResponse`
    (`ended_at = started_at + 10мин`) и создать новую `TenMinCheck` с
    `is_recovery = true`, `started_at = ended_at` предыдущей;
  - `ResolveNoResponse` на восстановительной → закрыть её как `NoResponse`,
    скопировать `reason` (если уже был получен) в исходную десятиминутку,
    открыть следующую обычную десятиминутку интервала (или завершить интервал,
    если это была 5-я).
  Никакого `Scheduler`/`JobId`/`cancel` в реализации нет и не нужно — вся
  "отмена" сводится к тому, что закрытая (`ended_at IS NOT NULL`) десятиминутка
  просто перестаёт попадать в `find_open()` на следующем тике.
- `SwitchTaskMidInterval(interval_id, new_task_id)` — реализация правила
  "задача готова" из SPEC.md: закрывает текущую задачу (`MarkTaskDone` из
  Задачи 6), переводит новую задачу в `in_progress`; оставшиеся (ещё не
  начавшиеся) десятиминутки этого часа создаются уже с `task_id = new_task_id`.
  Десятиминутка, уже находящаяся в процессе на момент вызова (её `ended_at`
  ещё `NULL`), НЕ прерывается и НЕ меняет `task_id` задним числом — она
  продолжает как обычно попадать в `find_open()`/`AdvanceOpenTenMinChecks` и
  завершается под прежней задачей естественным образом; специальной логики
  отмены здесь не требуется, потому что отменять нечего — нет отдельного
  запланированного job'а на текущую десятиминутку.
- `FinishHourInterval(interval_id, summary: String)` — закрывает интервал,
  считает `successful_count`, сохраняет `summary` (обязательный ответ "что
  делали за этот час") в `hour_intervals.summary`, вызывает Notifier с итогом
  интервала.

**Тестирование:**
- Сценарные тесты (given/when/then) на моках: полный happy path 5/5 → отдых
  засчитан; сценарий 3/5 → отдых не засчитан; сценарий "нет ответа" два раза
  подряд → 2 проваленные десятиминутки; ответ во время восстановительного окна
  останавливает напоминания, но не спасает статус; смена задачи посередине —
  каждый `TenMinCheck` после переключения имеет новый `task_id`.
- Тесты на `AdvanceOpenTenMinChecks` с фейковым `Clock` (единичные вызовы с
  заданным `elapsed`, без реального ожидания): обычная десятиминутка на 9-й
  минуте → `NoActionYet`; на 10-й (`[10,11)`) → `AskAreYouWorking`; без ответа
  на 11-й → `ResolveNoResponse`, десятиминутка закрыта `NoResponse`, создана
  восстановительная (`is_recovery = true`); восстановительная без ответа на
  каждой минуте её первых 10 минут → `RemindWhySilent` на каждом вызове, на
  10-й — `ResolveNoResponse`.

**Критерии приёмки:**
- Все сценарии из SPEC.md п.2 покрыты сценарными тестами.
- Ни один тест не спит реальное время (используется фейковый `Clock`).

## Задача 8. Application: use cases обеда и завершения дня

**Зависит от:** Задача 7.

**Цель:** обед и закрытие дня с проверкой нормы часов.

**Что реализовать:**
- `StartLunch(work_day_id)` / `EndLunch(work_day_id)` — фиксируют start/end,
  можно вызвать только между интервалами (не во время активного интервала).
- `SuggestLunchAfterNthInterval` — вспомогательная логика/событие (бот сам
  предлагает после 4-го интервала) — как доменное правило + вызов Notifier.
- `FinishWorkDay(work_day_id)` — закрывает день, считает итог (сколько из 8
  часовых интервалов закрыто, суммарное время по задачам, обеденное время
  отдельной строкой). Если на момент вызова есть активный незакрытый часовой
  интервал — он принудительно закрывается тем же путём, что и `FinishHourInterval`
  из Задачи 7, но без обязательного `summary` (пустой/`None`, вопрос "что делали
  за этот час" не блокирует завершение): `successful_count` считается по уже
  фактически произошедшим `TenMinCheck`, ещё не начавшиеся десятиминутки не
  создаются задним числом. Отдельно отменять что-либо не требуется — как только
  `ended_at` интервала и его открытых `TenMinCheck` проставлены, они перестают
  попадать в `find_open()` и больше не обрабатываются поллером (Задача 7/10).
- `PromptContinueIfIdle()` — **не вызывается планировщиком, а вызывается
  периодическим poll-циклом** (Задача 10) на каждом тике, аналогично
  `AdvanceOpenTenMinChecks` из Задачи 7. Реализация: запросить все открытые
  `work_days` без активного интервала
  (`WorkDayRepository::find_open_without_active_interval()` из Задачи 3); для
  каждого посчитать `elapsed = Clock.now() - (last_idle_prompt_at ИЛИ момент
  начала простоя — окончание последнего интервала/обеда/старт дня, смотря что
  позже)` и передать в чистую функцию `IdlePromptDecision` из Задачи 2 вместе
  с порогом `N` часов; если она вернула `true` — `Notifier.send("Готовы
  продолжить работу?")` и `work_days.last_idle_prompt_at = now`. Отдельной
  "отмены" не требуется: как только пользователь стартует интервал
  (`StartHourInterval`) — `work_day` перестаёт попадать в
  `find_open_without_active_interval()` и напоминания сами прекращаются на
  следующем тике; аналогично при `FinishWorkDay`. Автоматического завершения
  дня по таймауту нет — только периодическое напоминание.

**Тестирование:**
- Тест: обед нельзя начать во время активного незакрытого интервала (бизнес-ошибка).
- Тест: `FinishWorkDay` корректно исключает обеденное время из 8-часовой нормы.
- Тест: `FinishWorkDay`, вызванный во время активного интервала (например, после
  2 из 5 десятиминуток), принудительно закрывает интервал по фактическим 2
  десятиминуткам, не создаёт оставшиеся 3, отдых не начисляется (не 5/5).
- Тест: автопредложение обеда триггерится ровно после 4-го закрытого интервала,
  не раньше и не позже.
- Тест: `PromptContinueIfIdle` не выбирает `work_day` с активным часовым
  интервалом (не попадает в `find_open_without_active_interval()`).
- Тест на `IdlePromptDecision`/`PromptContinueIfIdle` с фейковым `Clock`:
  `elapsed < N часов` → `Notifier` не вызывается, `last_idle_prompt_at` не
  меняется; `elapsed >= N часов` → `Notifier` вызывается один раз за тик,
  `last_idle_prompt_at` обновляется на текущее время (следующий вызов сразу
  после этого снова возвращает `false`, пока не пройдёт ещё `N` часов).
- Тест: после `StartHourInterval` или `FinishWorkDay` соответствующий
  `work_day` перестаёт возвращаться `find_open_without_active_interval()`, и
  `PromptContinueIfIdle` больше не шлёт по нему напоминаний на следующих тиках
  (никакой отдельной операции "отмены" не вызывается — это следствие того, что
  запрос к БД просто больше не находит эту строку).

**Критерии приёмки:**
- Итоговые числа в `FinishWorkDay` сходятся с ручным расчётом на 2-3 заранее
  прописанных фикстурах-сценариях (golden test).
- Значение `N` (часы простоя до напоминания) читается из конфигурации, а не
  захардкожено (см. Задача 13).

## Задача 9. Application: отчёты и экспорт

**Зависит от:** Задача 8.

**Цель:** use cases для `/report` и экспорта в CSV.

**Что реализовать:**
- `BuildDayReport(work_day_id) -> ReportDto` — текстовое представление (время
  по задачам, провальные десятиминутки с причинами, обед, норма 8ч, а также
  `summary` каждого завершённого часового интервала — ответ на "что делали за
  этот час"). Если день ещё не закрыт и текущий часовой интервал не завершён —
  в отчёт попадают только уже завершённые десятиминутки этого интервала, сам
  интервал не считается "закрытым" для нормы 8 часов (см. SPEC.md п.5).
- `BuildPeriodReport(user_id, period: Week | Month, at: Option<NaiveDate>) -> ReportDto` —
  агрегированный отчёт за неделю/месяц: сумма отработанного времени и по
  задачам, число закрытых дней с выполненной нормой, суммарное обеденное время,
  по всем `work_days` пользователя, попадающим в период. Границы периода
  вычисляются по календарной дате `work_days.started_at`, сконвертированной из
  UTC в `users.timezone` (см. SPEC.md п.5) — не по UTC-дате. Если `at` не
  передан (команда без даты — обычный случай для `/report_week`/`/report_month`),
  "сегодня" вычисляется **внутри use case**, а не в Telegram-адаптере, как
  `Clock.now()` (порт из Задачи 3), сконвертированный в `users.timezone` — это
  бизнес-правило, а не забота адаптера, и должно жить в одном месте, иначе
  дублирование конвертации таймзоны разъедется между адаптерами. Использует тот
  же `ReportDto`, что и дневной отчёт (с полем периода).
- `ExportDayReportCsv(work_day_id) -> Vec<u8>` (CSV в памяти, отдаётся наружу
  через Notifier как `OutboundMessage::Document`, см. Задачу 3).
- `ReportDto`/CSV-формат — в `application`, без зависимости на конкретный формат
  вывода интерфейса (Telegram просто сериализует/отправляет).

**Тестирование:**
- Golden-тесты: фиксированный сценарий дня → сравнение с эталонной CSV-строкой
  и текстом отчёта (снапшот-тестирование).
- Golden-тест на `BuildPeriodReport`: фикстура из нескольких `work_days` внутри
  недели/месяца → сравнение агрегированных чисел с ручным расчётом; дни за
  пределами периода (с учётом таймзоны пользователя) не должны попадать в
  сумму (граничные даты периода).
- Тест: `BuildPeriodReport` без явного `at` для пользователя в часовом поясе
  восточнее UTC (например `UTC+7`), когда фейковый `Clock.now()` близок к
  полуночи по UTC, но уже следующий локальный день — период считается по
  локальной дате, а не по UTC-дате `Clock.now()`.

**Критерии приёмки:**
- CSV открывается в Excel/LibreOffice без искажений (проверить кодировку UTF-8,
  разделители).
- `BuildPeriodReport` корректно работает на границах периода (первый/последний
  день недели или месяца, разные часовые пояса пользователя).

## Задача 10. Poll-цикл на tokio

**Зависит от:** Задача 7 и Задача 8 (нужны use cases `AdvanceOpenTenMinChecks` и
`PromptContinueIfIdle`), может делаться параллельно с Задачами 5–9 в части
каркаса цикла, но по-настоящему протестирована будет только после них; нужна
перед Задачей 13.

**Цель:** вместо отдельного `Scheduler`-порта с job'ами (сознательно убран из
Задачи 3, см. SPEC.md п.4 — "таймер = пара UTC-полей, а не запланированное
задание") — простой периодический цикл на `tokio::time::interval`, который
каждый тик вызывает use cases из Задачи 7 и 8. Это единственный механизм
проактивных сообщений во всей системе.

**Что реализовать:**
- `PollLoop` — `tokio::time::interval(poll_interval)` (конфигурируемый, по
  умолчанию 60 секунд — совпадает с требуемой SPEC.md периодичностью "раз в
  минуту" для восстановительных десятиминуток, см. Задачу 7), на каждом тике
  вызывает `AdvanceOpenTenMinChecks()` и `PromptContinueIfIdle()`
  последовательно (или параллельно — порядок между ними не важен, это разные
  сущности).
- Никакого состояния между тиками цикл не хранит (ни `HashMap`, ни `JobId`) —
  вся нужная информация каждый раз перечитывается из БД через репозитории.
  Это делает цикл тривиально restart-safe: после рестарта процесса первый же
  тик отработает как обычно, просто увидит текущее состояние БД.

**Тестирование:**
- Тесты с `tokio::time::pause()`/`advance()` (виртуальное время) — не ждать
  реальные секунды в тестах: продвинуть время на несколько тиков вперёд и
  проверить, что use cases были вызваны ожидаемое число раз.
- Тест: `PollLoop`, запущенный заново на тех же данных БД (эмулирует рестарт
  процесса — просто новый экземпляр `PollLoop` без предыдущего состояния),
  ведёт себя идентично работающему без перерыва циклу — подтверждает
  restart-safety на уровне этого адаптера.

**Критерии приёмки:**
- Полный прогон нескольких тиков в тесте занимает <1 секунды реального времени
  благодаря паузе времени tokio.
- Реализация `PollLoop` укладывается в ~30-50 строк — никакой отдельной
  структуры данных для хранения "активных задач" не требуется (в отличие от
  прежнего `TokioScheduler`/`HashMap<JobId, JoinHandle>`).

## Задача 13. Composition root и конфигурация

**Зависит от:** Задачи 4, 9, 10, 12 (всё, что нужно собрать вместе).

**Цель:** `bin/app/main.rs` — единственное место, где собираются конкретные
реализации всех портов и передаются в use cases.

**Что реализовать:**
- Конфиг через `.env`/`config` крейт: путь к SQLite-файлу, Telegram-токен,
  интервал `N` часов простоя для `PromptContinueIfIdle` (Задача 8).
- Явная сборка: `SqliteUserRepository`, `TeloxideNotifier` → передаются в
  конструкторы use cases → use cases передаются в telegram-адаптер и в

  после старта видит текущее состояние БД и ведёт себя одинаково что после

**Тестирование:**
- Тест запуска: приложение стартует с тестовым конфигом и падает с понятной
  ошибкой при отсутствии обязательных переменных окружения.
- Интеграционный тест restart-safety на tempfile SQLite: создать открытый
  `work_day` с активным интервалом и незавершённой десятиминуткой напрямую
  через репозитории (эмулируя состояние "как будто процесс уже работал и упал"),
  затем поднять composition root с нуля (как при реальном рестарте) и
  убедиться, что ближайший тик `PollLoop` обрабатывает эту десятиминутку
  корректно — без какого-либо специального кода восстановления.

**Критерии приёмки:**
- `cargo run -p app` поднимает бота при валидном `.env`.
- Нет `unwrap()`/`expect()` на пользовательском вводе или сетевых вызовах вне
  явно задокументированных мест инициализации.

application-слой с реальной SQLite tempfile, mock-Notifier и фейковым `Clock`
с управляемым временем — никакого mock-планировщика не требуется, т.к.
таймеры полностью выражены через данные в БД; чисто через Telegram — вручную
по чек-листу).

**Сценарии (минимум):**
1. Регистрация нового пользователя первым любым сообщением.
2. Полный рабочий день: 8 интервалов, все 5/5 — отдых считается, норма 8ч выполнена.
3. Интервал с провалами (3/5) — время в задачу только 30 мин, отдых не считается.
4. Сценарий "нет ответа" — 2 проваленные десятиминутки подряд, включая случай
   ответа внутри восстановительного окна (статус всё равно проваленный).
5. Смена задачи посередине интервала — время корректно разбито между двумя
   задачами (через `task_id` на отдельных `TenMinCheck`).
6. Обед вручную посреди дня + обед по предложению после 4-го интервала.
7. `/report` в середине дня (включая незавершённый интервал) и `/finish_day` —
   числа совпадают.
8. Экспорт CSV — сверка вручную, отправляется как документ (не текстом).
9. День начат, интервал не стартован дольше `N` часов — приходит периодическое
   напоминание "Готовы продолжить работу?"; после старта интервала повторные
   напоминания прекращаются; день не завершается автоматически.
10. `/report_week` / `/report_month` за период с несколькими рабочими днями —
    агрегированные числа совпадают с ручным расчётом по исходным дням, с учётом
    таймзоны пользователя на границах периода.
11. Задача с приоритетом и дедлайном корректно сохраняется/отображается в пуле
    задач.
12. Создание/редактирование задачи через бота (`CreateTask`/`UpdateTask` из
    Задачи 6) и корректная сортировка/фильтрация пула задач (`ListAvailableTasks`)
    по приоритету и дедлайну.
13. `/finish_day` во время активного часового интервала (не все 5 десятиминуток
    пройдены) — интервал закрывается по фактическим десятиминуткам, отдых не
    начисляется, день корректно завершается без зависших таймеров.
14. Рестарт процесса с открытым днём: активный интервал с незавершённой
    десятиминуткой (или день без активного интервала) — после перезапуска
    напоминания (эскалация "молчания" / `PromptContinueIfIdle`) продолжают
    приходить без какого-либо специального кода восстановления, просто
    потому что `PollLoop` (Задача 10) каждый тик заново читает состояние из
    БД (см. SPEC.md п.4).

**Критерии приёмки MVP:**
- Все 14 сценариев проходят как автотесты (или задокументированы как ручной
  чек-лист с результатом, если e2e через Telegram недостижим в CI).
- `README.md` в корне репозитория обновлён: как запустить, архитектура,
  ссылка на SPEC.md и этот файл.
- Итог: рабочая первая версия бота, доступная через Telegram, данные переживают
  перезапуск процесса (SQLite-файл персистентен).
